# Редактор шаблонов подписок Remnawave — дизайн

Дата: 2026-09-03
Статус: одобрен пользователем (брейнсторминг завершён)
Источник: [issue #43](https://github.com/VAQYBIN/Remnawave-Xray-UI-Editor/issues/43), трек 3

## Цель

Дать редактору вторую сущность панели — **шаблоны подписок** (Subscription
Templates), то есть конфиги, которые получают клиентские приложения. Сейчас
редактор работает только с конфиг-профилями нод.

Автор issue просил визуально править шаблон, «не ломая динамические элементы»,
и предполагал текстовые плейсхолдеры вида `{{inbounds}}`, которые делают
документ невалидным JSON. **Механизм Remnawave устроен иначе**, и это меняет
задачу в нашу пользу — см. следующий раздел.

## Как устроена подстановка на самом деле

Шаблон всегда остаётся валидным JSON. Подстановка задаётся обычным объектом
`remnawave` в корне, рядом с `dns`, `routing`, `inbounds`, `outbounds`:

```json
{
  "remnawave": {
    "addVirtualHostAsOutbound": false,
    "injectHosts": [
      {
        "selector": { "type": "tagRegex", "pattern": "^RU-" },
        "tagPrefix": "proxy",
        "selectFrom": "HIDDEN"
      }
    ]
  },
  "dns": { "servers": ["1.1.1.1"] },
  "routing": { "rules": [] },
  "outbounds": [{ "tag": "direct", "protocol": "freedom" }]
}
```

Панель выбирает хосты по селектору, строит из них outbound'ы, **вставляет их в
начало массива** `outbounds` и удаляет сам объект `remnawave` перед отдачей
клиенту. Теги получаются `proxy`, `proxy-2`, `proxy-3` — либо из примечания или
тега хоста.

Селекторы: `uuids`, `remarkRegex`, `tagRegex`, `sameTagAsRecipient`.
Пул выбора `selectFrom`: `HIDDEN` (по умолчанию), `NOT_HIDDEN`, `ALL`.
Способ именования — **ровно один** из `tagPrefix`, `useHostRemarkAsTag`,
`useHostTagAsTag`.

Документация: <https://docs.rw/learn/xray-json-advanced/>.

Три следствия, каждое сокращает работу:

1. **Парсер «сломанного JSON» не нужен.** Это был главный предполагаемый риск.
2. **XRAY_JSON-шаблон — это тот же Xray-конфиг**, что мы уже редактируем.
   Существующий конвейер (разбор → граф → формы → генерация) ложится на него.
3. **Префиксное сопоставление тегов уже написано.** `routing.balancers[].selector`
   матчит `proxy`, `proxy-2` по префиксу — это `matchPrefixes` в
   `entities/xray/balancers.ts`.

`XrayConfigSchema` — `z.looseObject`, поэтому ключ `remnawave` уже сегодня
переживает цикл разбор → правка → генерация и не теряется. Задача — его
типизировать и показать, а не сохранить.

## Ключевые решения (из брейнсторминга)

| Вопрос | Решение |
|---|---|
| Охват типов | Сначала XRAY_JSON; затем Mihomo, Clash, Stash; Sing-box последним |
| Показ `injectHosts` | Узлы в колонке outbound, наравне с обычными выходами |
| Защита при сохранении | Сравнение содержимого (хэш), `updatedAt` у шаблонов нет |
| Инструментарий v1 | Диагностики и трассировка. Без проверки ядром и рецептов |
| Создание и удаление | Входят в первую версию |
| Архитектура | Отдельная страница шаблонов + вынос общей оболочки из `EditorPage` |
| Официальный SDK | `@remnawave/backend-contract` как devDependency: только типы |

## Контракт панели

Проверено по официальному пакету `@remnawave/backend-contract@3.4.14`
(единственная зависимость — `zod`), а не по документации и не по стороннему SDK.

```
GET    /api/subscription-templates/          список (содержимое приходит null)
POST   /api/subscription-templates/          { name, templateType }
GET    /api/subscription-templates/{uuid}    один шаблон с содержимым
PATCH  /api/subscription-templates/          { uuid, name?, templateJson?, encodedTemplateYaml? }
DELETE /api/subscription-templates/{uuid}    { response: { isDeleted } }
```

Объект шаблона: `{ uuid, viewPosition, name, tags, templateType, templateJson,
encodedTemplateYaml }`.

Типы: `XRAY_JSON`, `XRAY_BASE64`, `MIHOMO`, `STASH`, `CLASH`, `SINGBOX`.

**Полей `createdAt`/`updatedAt` нет.** Оптимистическая блокировка через
`expectedUpdatedAt`, на которой держится сохранение профилей, здесь неприменима.

## 1. Модель данных

Новый файл `entities/xray/inject.ts` по образцу `balancers.ts` и `observatory.ts`:

```
HostSelector = discriminatedUnion('type'):
  { type: 'uuids',       values: string[] }
  { type: 'remarkRegex', pattern: string }
  { type: 'tagRegex',    pattern: string }
  { type: 'sameTagAsRecipient' }

InjectGroup = looseObject:
  selector: HostSelector
  selectFrom?: 'HIDDEN' | 'NOT_HIDDEN' | 'ALL'
  tagPrefix? | useHostRemarkAsTag? | useHostTagAsTag?

RemnawaveDirectives = looseObject:
  addVirtualHostAsOutbound?: boolean
  injectHosts?: InjectGroup[]
```

В `XrayConfigSchema` добавляется `remnawave?: RemnawaveDirectives`.

**Отдельного типа конфига для шаблонов нет.** Иначе пришлось бы форкать
сигнатуры `validate`, `trace`, `generate` и всех мутаций ради одного
необязательного ключа. Колонка подстановки рисуется по наличию
`remnawave.injectHosts`; у профиля ноды этого ключа не бывает, поэтому
флаг-переключатель не нужен.

### Предсказание тегов — и границы знания

Инжектируемых outbound'ов в конфиге физически нет, а балансеры и правила
ссылаются на них по тегу. Группа объявляет не список тегов, а их образец, и это
знание **неполное**:

- `tagPrefix: "proxy"` — теги предсказуемы (`proxy`, `proxy-2`, …), связи
  выводимы и проверяемы;
- `useHostRemarkAsTag` / `useHostTagAsTag` — теги приходят из данных панели и
  заранее **неизвестны**.

Функция «какие теги произведёт эта группа» живёт рядом с моделью;
`matchPrefixes` из `balancers.ts` остаётся единственной реализацией
сопоставления.

## 2. Бэкенд

**Порт и типы.** В `remnawave/types.ts` — `SubscriptionTemplate`; в
`RemnawavePort` — `listTemplates`, `getTemplate`, `createTemplate`,
`updateTemplate`, `deleteTemplate`. Реализация в `RemnawaveClient` — близкий
аналог профильных методов: панель дала ту же форму ручек. Стаб в тестах
расширяется теми же методами.

**Роуты** (`backend/src/routes/templates.ts`, по образцу `profiles.ts`):

```
GET    /api/templates          → { templates }          только метаданные
POST   /api/templates          → 201 { template }
GET    /api/templates/:uuid    → { template, hash }
PATCH  /api/templates/:uuid    → { template } | 409 { message, current }
DELETE /api/templates/:uuid    → { ok: true }
```

**Обнаружение конфликта.** Хэш считает **только бэкенд**. При чтении отдаётся
`hash` — sha256 от канонического JSON, где канонизация означает рекурсивную
сортировку ключей объектов (порядок элементов массивов значим и сохраняется).
Хэшируется **только `templateJson`**: имя правится отдельным полем формы, и
переименование в панели не должно объявляться конфликтом содержимого.
Клиент хранит хэш в черновике
рядом с тем, как хранит `baseUpdatedAt` для профилей, и возвращает при
сохранении. Бэкенд перечитывает шаблон, считает хэш тем же кодом и сравнивает.
Канонизация живёт в одном месте, и стороны не могут разойтись на порядке ключей.
Форма ответа `409` совпадает с профильной, поэтому `SaveDialog` и `ConflictError`
работают без правок.

**Создание одношаговое для пользователя.** У панели оно двухшаговое: `POST`
делает пустой шаблон, содержимое заливается отдельным `PATCH`. Склейка — на
бэкенде, клиент видит одну операцию. Заполняется каркасом, а не пустотой:
локальные socks/http inbound'ы, `direct` и `block`, пустой `routing` и одна
группа `injectHosts` с `tagPrefix: "proxy"`. Пустой шаблон бесполезен, этот
сразу рабочий.

**Тип при создании — только `XRAY_JSON`.** Предлагать создать шаблон, который
тут же нельзя открыть, — обман. Список типов вырастет вместе с редакторами.

**Бэкапы.** `BackupService.saveBackup` типизирован под `ConfigProfile` и пишет в
`DATA_DIR/backups/<uuid>/`. Добавляется необязательное пространство имён:
шаблоны уходят в `DATA_DIR/backups/templates/<uuid>/`, путь профилей не
меняется — иначе накопленные бэкапы осиротеют. Бэкап пишется и перед
обновлением, и **перед удалением**: удалённый шаблон остаётся восстановимым.

**Ошибки** переиспользуются целиком: `RemnawaveError` уже заворачивает ответы
панели, 401/403 превращаются в 502 с подсказкой про токен.

### Использование официального SDK

`@remnawave/backend-contract` подключается как **devDependency** и только через
`import type` — такие импорты стираются при сборке, в рантайме пакета нет.
Плюс контрактный тест на уровне типов: отдельный файл с проверками
присваиваемости (наш `SubscriptionTemplate` ← тип ответа пакета и обратно),
который ничего не выполняет в рантайме, а падает на `tsc --noEmit`. Это ставит
обнаружение дрейфа в тот же шаг CI, где уже крутится typecheck.

Почему не глубже. Пакет привязан к версии панели (634 релиза, таблица
совместимости, прямое указание «pin the correct version»), а его zod-схемы
строгие. Прогонять через них ответы означало бы падение редактора на панели
новее нашего пина. В треке 1 мы убедились в обратном поведении: панель 3.4.0
добавила профилям `tags`, и ничего не сломалось именно потому, что ответы не
валидируются — это закреплено тестом «новые поля панели проходят насквозь».
README обещает работу и с 2.8.x, и с 3.x; строгий контракт под одну версию это
обещание подрывает.

Что пакет при этом даёт: контракт из первых рук вместо реверс-инжиниринга и
обнаружение дрейфа в CI при обновлении версии. Пользы это уже принесло —
сверка исправила три ошибки, взятые из стороннего Rust SDK: URL коллекций со
слешем на конце, необязательность `name` в теле `PATCH` и состав перечисления
типов (есть `XRAY_BASE64`, нет `SINGBOX_LEGACY`).

## 3. Граф и мутации

**Узел подстановки.** Вид `inject` в `entities/graph/types.ts`, id
`inj:<индекс>` — по образцу правил (`rule:<индекс>`). Живёт в колонке outbound
**выше статических выходов**: панель вставляет инжектируемые outbound'ы в начало
массива. На карточке — селектор, пул, схема тегов и предсказанные теги.

**Рёбра.** Группа с `tagPrefix` соединяется с балансером, чей `selector`
префиксно с ней совпадает, и с правилом, чей `outboundTag` равен предсказанному
тегу. Группа с `useHost*AsTag` рисуется с пометкой «теги задаёт панель», и
входящих рёбер к ней не выводится.

**Мутации** (`entities/graph/mutations.ts`): `addInjectGroup`,
`updateInjectGroup`, `removeInjectGroup`. Протяжка «правило → группа» ставит
`outboundTag` в первый предсказанный тег; «балансер → группа» добавляет префикс
в `selector`. Разрыв префиксного ребра — уже решённая задача: `disconnectEdge`
возвращает тот же конфиг, `TopologyView` спрашивает подтверждение и зовёт
`expandSelector`.

**Коммутация** (`isValidConnection`): добавляются пары `rule: → inj:` и
`bal: → inj:`. Подсветка валидных целей подхватит это сама — она читает набор
колонок из самой `isValidConnection`.

**Осознанный размен:** id по индексу означает, что перестановка групп в JSON
меняет id узлов. Для правил в проекте это уже принято; синтетические ключи ради
подстановки не заводим.

## 4. UI

**Роуты.** Добавляются `/templates` и `/templates/:uuid`. Переключение между
разделами — сегментированный переключатель «Профили | Шаблоны» в шапке обоих
списков; кнопка возврата в редакторе шаблона ведёт на `/templates`.

**Вынос общей оболочки.** Из `EditorPage` (709 строк) выносится:

- `useConfigDraft` — логика документа: черновик в localStorage, история
  undo/redo, валидация, выбор узла, единая точка записи `writeDraft`;
- `Workbench` — раскладка топбар / сцена с вкладками «Топология | JSON» /
  статус-бар вместе с диалогами сохранения и версий.

После этого обе страницы становятся тонкими и симметричными: каждая знает свой
источник данных, своё сохранение и свой набор кнопок топбара. `EditorPage` при
этом худеет.

**Список шаблонов** (`features/templates/TemplatesPage.tsx`) — карточки по
образцу профилей: имя, бейдж типа, теги. XRAY_JSON открывается в редакторе;
карточки остальных типов показаны с пометкой «редактор пока не поддерживает,
откройте в панели». Скрывать их нельзя — иначе список врёт о содержимом панели.

**Создание** — `CreateTemplateDialog` по образцу `CreateProfileDialog`.
**Удаление** — из карточки, с подтверждением.

**Форма группы инжекта** (`features/inspector/InjectGroupForm.tsx`): тип
селектора, его параметр, пул `selectFrom`, схема тегов. Инвариант «ровно одно из
трёх» форма делает невыразимым: выбор одного способа снимает остальные — тот же
приём, что уже применён к паре `outboundTag`/`balancerTag`.

**В топбаре шаблона нет** «Проверить конфиг» и «+ Рецепт». «Куда пойдёт трафик»
есть.

**Сквады.** `GraphContext` для шаблона пустой. `buildGraph` уже фильтрует сквады
по реально существующим тегам инбаундов, поэтому пустой контекст просто не даёт
колонку — специального кода не нужно.

## 5. Диагностики и трассировка

Проверки живут одной функцией в `entities/xray/config.ts` и складывают проблемы
с путём-массивом `parts`. На `parts` завязаны три резолвера — переход к месту в
JSON, переход к узлу графа и поиск, — поэтому новые проверки получают их
бесплатно.

| Проверка | Уровень |
|---|---|
| Группа без `selector` или с неизвестным типом селектора | ошибка |
| Не выбран ни один способ именования тегов — или выбрано больше одного | ошибка |
| `remarkRegex` / `tagRegex` не компилируется как регулярное выражение | ошибка |
| `selectFrom` вне `HIDDEN` / `NOT_HIDDEN` / `ALL` | ошибка |
| Селектор `uuids` с пустым списком | предупреждение |
| В шаблоне нет ни одной группы инжекта | предупреждение |

Последняя — самая ценная: именно она отвечает подписке без единого сервера, и
глазами в JSON это не видно.

**Что ослабляется.** Две существующие проверки — «правило ссылается на
неизвестный outbound-тег» и «у балансера нет кандидатов» — дают на корректном
шаблоне ложную тревогу, потому что теги `proxy`, `proxy-2` в конфиге
отсутствуют. Правило:

- статические outbound'ы дополняются **предсказанными** тегами групп с
  `tagPrefix`, и проверки работают как раньше;
- если есть хоть одна группа с `useHost*AsTag`, обе проверки подавляются
  целиком.

Это осознанный размен в сторону пропуска опечатки. Редактор, который ругается на
исправный документ, перестают читать вообще — и тогда теряются все остальные
предупреждения.

**Трассировка.** В `trace.ts` меняется не обход правил, а разрешение тега в
выход: совпадение с предсказанным тегом даёт «уйдёт в группу подстановки:
`tagRegex ^RU-`, пул HIDDEN»; неизвестные теги — «сервер подставит панель»
вместо нынешнего «неизвестный outbound». Балансер уже поддержан, его список
кандидатов дополняется предсказанными тегами через ту же `matchPrefixes`.

Для шаблона подписки трассировка полезнее, чем для профиля ноды: здесь живёт
клиентская маршрутизация и сплит-туннель, ради которых шаблоны и правят руками.

## 6. Тестирование

**Бэкенд:** роуты шаблонов, конфликт `409` по хэшу, бэкапы в своём пространстве
имён, склейка создания — на расширенном `stub-remnawave`. Отдельно проверяется,
что канонизация устойчива к порядку ключей: один и тот же документ с ключами в
разном порядке даёт один хэш, изменение значения — разный. Плюс контрактный
тест на уровне типов против `@remnawave/backend-contract`.

**Фронтенд-юниты:** разбор и round-trip модели инжекта, предсказание тегов, узлы
и рёбра в `buildGraph`, мутации, каждая новая валидация **и обе подавляемые** —
на подавление тесты нужны не меньше, чем на срабатывание, иначе ослабление
незаметно превратится в дыру. Форма проверяется на инвариант «ровно одно из
трёх».

**E2E:** открыть шаблон, поправить группу, соединить балансер с ней, сохранить,
поймать конфликт, создать и удалить.

**Живая проверка:** прогон записи на временном шаблоне против панели, как в
треке 1.

## Порядок работ

Снизу вверх, каждый шаг заканчивается зелёными тестами:

1. Бэкенд целиком: порт, клиент, роуты, бэкапы, хэш конфликта.
2. Модель `inject.ts`, предсказание тегов, валидации — чистые функции, без UI.
3. Граф: узлы, рёбра, мутации, коммутация.
4. **Вынос `useConfigDraft` и `Workbench` из `EditorPage`** — чистый рефакторинг
   без изменения поведения.
5. Страницы: список, создание, удаление, редактор шаблона.
6. Форма группы инжекта.
7. Трассировка.
8. E2E и проверка записи на живой панели.

Шаг 4 стоит именно здесь намеренно: делить `EditorPage` надо **до** появления
второй страницы, пока существующие фронтенд-тесты служат сеткой безопасности.
Если сначала написать `TemplateEditorPage`, рефакторить придётся две страницы
сразу и без сетки.

## Риски

- **Запись ни разу не выполнялась вживую.** Контракт взят из официального
  пакета, но `PATCH`, `POST` и `DELETE` не отправлялись. Первый шаг реализации —
  прогон на временном шаблоне.
- **Канонизация для хэша.** Считает только бэкенд; клиент хэш не вычисляет,
  иначе стороны разойдутся на порядке ключей.
- **Дрейф контракта.** Пакет версионируется под панель. Обновление версии —
  осознанное действие, а не автоматическое: контрактный тест покажет расхождение,
  но чинить его придётся руками.

## Вне охвата

- Редакторы MIHOMO, CLASH, STASH, SINGBOX, XRAY_BASE64 — отдельными итерациями
  в порядке: Mihomo, Clash, Stash, затем Sing-box.
- Проверка шаблона ядром Xray и рецепты — возможны позже; ядро потребует снятия
  объекта `remnawave` и подстановки фиктивных outbound'ов вместо инжектируемых.
- Теги шаблонов (`tags`) — редактор их сохраняет, но не редактирует.
