# Диагностика конфига: трассировщик правил, проверка ядром, проверка Reality-цели

Дата: 2026-07-25. Статус: дизайн утверждён, декомпозиция на 3 плана реализации.

## Проблема

Редактор умеет собирать конфиг формами и проверять его схемой, но не умеет ответить на два
вопроса, которые возникают каждый раз перед сохранением в панель:

1. **Куда на самом деле уйдёт трафик?** Правила проверяются сверху вниз, побеждает первое
   совпавшее. Сейчас этот порядок проверяется только глазами, и ошибка в приоритете правил —
   самая частая: правило-ловушка выше нужного молча забирает весь трафик.
2. **Запустится ли конфиг вообще?** `analyzeIntegrity` — набор эвристик (матрица
   security×network, висячие теги, формат портов). Всё остальное узнаётся уже после
   применения конфига на ноды.

Отдельно стоит третий вопрос, специфичный для selfsteal-нод: **годится ли выбранный
Reality-`target`** (TLS 1.3, ALPN h2, X25519, сертификат, не CDN). Неподходящая цель — типовая
причина «Reality палится» и «handshake fail», и проверить её из UI сейчас нельзя.

## Рамки

**Входит:** трассировщик маршрута по правилам с честными состояниями вердиктов; geo-подсистема
(разбор `geosite.dat`/`geoip.dat`, настраиваемые источники, обновление из UI); проверка конфига
бинарём Xray (`run -test`); проверка Reality-цели; UI — строка трассировки в доке графа,
подсветка победившего пути, разбор по правилам, диалог отчёта, диалог geo-баз; предупреждение о
выключенном sniffing в `analyzeIntegrity`.

**Не входит:** резолв доменов в IP силами сервера (вместо него — необязательное поле «IP
назначения»); выбор конкретного outbound за балансером (требует observatory); разбор
`ext:`-списков и `attrs` в правилах; автообновление geo-баз по расписанию.

## Принятые решения

1. **Логика трассировки — на фронте**, чистой функцией в `entities/xray`. Бэкенд отвечает
   только на узкий вопрос «входит ли домен/IP в такие-то geo-категории».
2. **Geo-данные качаются отдельно.** Релизный архив Xray-core geo-файлов не содержит (сверено
   с ассетами релиза v26.3.27 на 2026-07-25) — источник настраивается.
3. **Источники geo настраиваются из UI**, не через env: URL живут в `DATA_DIR/settings.json`,
   дефолты v2fly зашиты константами. Один источник правды, смена базы без редеплоя.
4. **Деградация вместо ошибок.** Нет geo-данных — вердикт «зависит от geo-списка»; нет бинаря
   Xray — «инструмент недоступен». Ни то, ни другое не ломает редактор.
5. **Честная неопределённость.** Трассировщик никогда не выдаёт догадку за факт: там, где
   данных нет, состояние `unknown` с объяснением причины.

## Дизайн

### 1. Разделение ответственности

Фронт извлекает из правил все geo-ключи, одним запросом получает
`Record<ключ, boolean>` и дальше считает маршрут синхронно. Ответы кэшируются react-query по
ключу `['geo', domain, ip, keys]`.

Альтернатива — считать весь маршрут на бэкенде (`POST /api/tools/trace` с конфигом в теле) —
отвергнута: доменная логика уехала бы из `entities/xray`, где лежит остальная семантика Xray,
каждый ввод в поле стал бы сетевым запросом, а тесты матчинга потребовали бы поднятого сервера.

### 2. Трассировщик (`entities/xray/trace.ts`)

```
traceRoute(config, target, geoAnswers) → TraceResult
```

- `target`: `address`, `port`, `network` (tcp/udp), необязательные `ip`, `user`, `inboundTag`,
  `protocol`.
- `geoAnswers`: `{ answers: Record<string, boolean>, missing: string[], loaded: boolean }` по
  ключам вида `geosite:google`, `geosite:google@ads`, `geoip:ru`. Три состояния ключа
  различаются намеренно: есть ответ; база загружена, но категории в ней нет (`missing` —
  ошибка конфига, не неопределённость); база не загружена (`loaded: false` — тогда все
  geo-ключи неизвестны).
- `TraceResult`: `verdicts: RuleVerdict[]`, `winner?: { index, outboundTag | balancerTag }`,
  `caveats: string[]`.
- `RuleVerdict`: `{ index, result: 'match' | 'no-match' | 'unknown', fields: FieldVerdict[] }`,
  где `FieldVerdict` объясняет по каждому **заданному** полю правила, совпало оно или нет.

**Семантика Xray реализуется буквально:** поля правила соединяются через И, значения внутри
поля — через ИЛИ, побеждает первое полностью совпавшее правило. Из этого следуют состояния:

- `no-match` — хотя бы одно заданное поле точно не совпало (перевешивает `unknown`, потому что
  поля соединены через И);
- `unknown` — все заданные поля совпали, но хотя бы одно опирается на недоступные данные;
- `match` — все заданные поля совпали на известных данных.

Если `unknown` встречается **выше** победителя, в `caveats` попадает предупреждение: реальный
маршрут может отличаться от показанного.

**Матчеры:**

- домен: без префикса — keyword-подстрока (переиспользуем логику `keywordEntries` из
  `rules.ts`), плюс `domain:` (сам домен и поддомены), `full:`, `regexp:`, `geosite:cat@attr`,
  `ext:` (всегда `unknown`);
- IP: точный адрес, CIDR, `geoip:cc` и инверсия `geoip:!cc`;
- порты: к существующему `portSpecError` добавляется `portMatches` (одиночные, диапазоны,
  списки);
- остальные поля: `network`, `source`, `sourcePort`, `user`, `inboundTag`, `protocol`.

**Две тонкости, без которых трассировщик врал бы:**

- **`routing.domainStrategy`.** При `AsIs` ядро не резолвит домен, поэтому ip/geoip-правила по
  доменной цели не срабатывают вовсе. При `IPIfNonMatch` выполняется второй проход по
  разрешённому адресу, при `IPOnDemand` — резолв при первом ip-правиле. Сервер домены не
  резолвит: в форме есть необязательное поле «IP назначения», и трассировщик показывает оба
  прохода, помечая, какой из них гипотетический.
- **`sniffing`.** Если правило матчит по `domain` или `protocol`, а на inbound'е sniffing
  выключен, ядро этих данных не увидит и правило не сработает. Проверка добавляется и в
  `analyzeIntegrity` (уровень warning) — сейчас её там нет.

Правило через `balancerTag` даёт победителя вида «балансер X» без выбора конкретного outbound.

### 3. Geo-подсистема (`backend/src/geo/`)

- `dat.ts` — разбор формата: два protobuf-сообщения (`GeoSiteList` из `GeoSite`
  с `country_code` и `domain[]`; `GeoIPList` из `GeoIP` с `country_code` и `cidr[]`). Пишем
  минимальный декодер varint и length-delimited полей вместо новой зависимости: формат
  стабилен, объём — около полутора сотен строк, тестируется на фикстуре, собранной тем же
  кодом.
- `store.ts` — ленивая загрузка файлов из `DATA_DIR/geodata/`, индекс в памяти
  (`Map<категория, matcher>`), инвалидация при обновлении файла. Индекс строится один раз на
  файл, а не на запрос.
- `POST /api/tools/geo/match` — `{ domain?, ip?, keys: string[] }` →
  `{ answers: Record<string, boolean>, source: { geosite, geoip } }`. Ключи, которых нет в
  базе, в `answers` не попадают — фронт трактует их как `unknown`.

**Настройки и обновление:**

- `backend/src/settings/` — маленький сервис рядом с `backups/`, состояние в
  `DATA_DIR/settings.json`;
- `GET`/`PUT /api/settings/geo` — URL источников; `POST /api/tools/geo/update` — загрузка
  файлов с проверкой размера и таймаутом, запись атомарной подменой;
- дефолты (зашиты константами): geosite — `dlc.dat` из `v2fly/domain-list-community`,
  geoip — `geoip.dat` из `v2fly/geoip`. Готовая альтернатива в подсказке UI —
  `Loyalsoldier/v2ray-rules-dat` (оба файла в одном релизе, расширенные категории вида
  `category-ads-all`, `geoip:telegram`).

Диалог «Geo-базы» показывает URL с пресетами, кнопку загрузки, дату файла и число категорий.
Это не украшение: трассировщик должен опираться на те же списки, что стоят на нодах, иначе он
будет уверенно врать — и пользователь обязан видеть, какие данные загружены.

### 4. Проверка ядром

`POST /api/tools/xray-test` — `{ config }` →
`{ available, ok, version?, errors: { line?, message }[] }`.

- путь к бинарю — `XRAY_BIN` (по умолчанию `xray`); бинарь не найден → `available: false`, UI
  показывает «инструмент недоступен» вместо ошибки, локальная разработка на Windows не
  ломается;
- конфиг пишется во временный файл внутри `DATA_DIR`, запускается `xray run -test -c`, таймаут
  10 секунд, вывод разбирается на сообщения; известные шаблоны маппятся на русские подсказки,
  остальное показывается как есть;
- **инжект фиктивного клиента.** Профили Remnawave хранятся с `clients: []` — пользователей
  инжектит панель. Прогон такого конфига дал бы ложные ошибки на том, что в проде валидно,
  поэтому перед тестом в vless/trojan/shadowsocks-inbound'ы подставляется один фиктивный
  клиент с валидным UUID. Преобразование чистое, живёт отдельной функцией со своими тестами; в
  UI отчёт отмечает, что проверялся конфиг с подставным пользователем.

Docker: бинарь добавляется в образ с pin версии и проверкой sha256 из `.dgst`-файла релиза
(актуальна v26.3.27 — та же версия, с которой в Xray появился Hysteria2-inbound), multi-stage,
чтобы архив не оставался в финальном слое.

### 5. Проверка Reality-цели

`POST /api/tools/reality-target` — `{ target: "host:port", serverNames: string[] }` → вердикты.

Реализация на Node: `tls.connect` с `ALPNProtocols: ['h2', 'http/1.1']`, затем `getProtocol()`,
`getCipher()`, `getEphemeralKeyInfo()` (даёт X25519) и `getPeerCertificate()`. Проверяем: TLS
1.3 — обязательно; ALPN h2 — желательно; сертификат должен покрывать `serverNames` (сверяем с
CN и SAN). Признаки CDN — мягкое предупреждение по совпадению эмитента сертификата или SAN со
списком известных строк CDN-провайдеров; список короткий, зашит константой и расширяется по
мере надобности. Эвристику подаём как подозрение, а не как вердикт.

Своя реализация предпочтена `xray tls ping`, потому что даёт структурированный результат вместо
текста на разбор и работает даже без бинаря ядра.

**Ограничение исходящих запросов:** перед подключением хост резолвится, приватные, loopback и
link-local адреса отклоняются; порт берётся из конфига; таймаут 5 секунд; редиректы не
следуются. Приложение однопользовательское, но давать серверу произвольные коннекты по запросу
из браузера незачем.

### 6. UI (`features/diagnostics/`)

- `TraceBar` — строка трассировки в существующем `wb-dock` (адрес, порт, network,
  необязательный IP назначения);
- `TracePanel` — разбор по правилам оверлеем, тем же приёмом, что инспектор;
- `CheckReportDialog` — отчёт проверки ядром и Reality-цели, вызывается кнопкой «Проверить
  конфиг» в топбаре;
- `GeoDataDialog` — источники, загрузка, версии.

`buildGraph` не меняется: вердикты правил и подсветка победившего пути прокидываются через
`data`, там же, где сейчас живёт `data.active` у рёбер. Состояние трассировки держится в
`EditorPage` без персиста — это инструмент, а не документ, и в localStorage ему делать нечего.

### 7. Тестирование

- **vitest (фронт)**: `trace.ts` — таблица кейсов на каждый матчер (keyword против `domain:`
  против `full:`, регексп, диапазоны портов, инверсия `geoip:!cc`), И-семантика полей,
  протекание `unknown`, приоритет `no-match` над `unknown`, оба прохода `domainStrategy`,
  «первое совпавшее побеждает», caveat при `unknown` выше победителя.
- **vitest (бэк)**: декодер `.dat` на фикстуре, стор (индекс, инвалидация), инжект фиктивного
  клиента, разбор вывода `xray -test`, деградация без бинаря, отклонение приватных адресов в
  проверке Reality-цели.
- **Playwright e2e**: трассировка в графе (ввод → подсветка пути и разбор по правилам), отчёт
  «Проверить конфиг» при недоступном ядре, диалог geo-баз. Как обычно, через `e2e/mocks.ts` —
  бэкенд не нужен.

## Декомпозиция на планы реализации

Каждый этап оставляет работающее состояние:

1. **Трассировщик** — `entities/xray/trace.ts`, `TraceBar`/`TracePanel`, вердикты и подсветка в
   графе, предупреждение о выключенном sniffing в `analyzeIntegrity`. Geo-ключи дают
   `unknown` — фича полезна уже здесь.
2. **Geo-подсистема** — декодер, стор, `/api/tools/geo/match`, настройки и обновление,
   `GeoDataDialog`. Превращает `unknown` в точные вердикты.
3. **Проверка ядром и Reality-цели** — `/api/tools/xray-test`,
   `/api/tools/reality-target`, `CheckReportDialog`, бинарь Xray в Docker-образе.

## Границы и риски

- `ext:`-списки, `attrs` и правила через `balancerTag` всегда дают `unknown` — это заявленное
  ограничение, а не дефект.
- Точность трассировки равна точности загруженной geo-базы. Если на нодах стоят другие списки,
  вердикты по geo-правилам разойдутся с реальностью; поэтому UI показывает источник и дату.
- Проверка ядром валидирует конфиг с подставным пользователем, то есть не ровно тот документ,
  что уйдёт в панель. Отклонение сознательное и отражено в отчёте.
- Бинарь Xray увеличивает Docker-образ примерно на 25–30 МБ и требует обновления pin-версии
  при выходе новых релизов ядра.
