# Наборы правил Mihomo в редакторе: загрузка, разбор, трассировка

**Дата:** 2026-09-08
**Статус:** согласовано, план не написан
**Предшественник:** `2026-09-05-mihomo-templates-design.md` (редактор шаблонов Mihomo)

## Цель

Довести трассировку Mihomo до состояния, в котором она отвечает на вопрос «куда
уйдёт трафик» на живом шаблоне, а не останавливается в начале списка.

Задача не косметическая, и её размер измерен, а не оценён. Эталон —
`by-roscomvpn/subscription-templates/roscomvpn-mihomo-ru.yaml` из каталога
`remnawave/templates`: 31 правило, 26 из них `RULE-SET`. Проверка сделана
подстановкой — все `RULE-SET` заменялись на заведомо не совпадающее правило с
сохранением позиций, после чего запускалась настоящая трассировка.

| Состояние | Докуда доходит проход |
|---|---|
| До правки `no-resolve` | правило #1 |
| Сейчас (`8adf32e`) | правило #4 |
| Если наборы отвечают | правило #25 |
| Цель | правило #31, `MATCH,PROXY` |

Из этого следует, что одних наборов недостаточно: за ними стоит вторая стена, и
она про процесс. Правило #25 — `RULE-SET,torrent-clients` с
`behavior: classical`, а внутри у него 90 строк, все до единой `PROCESS-NAME`;
правила #26–27 — `PROCESS-NAME-REGEX`. Цель, не совпавшая ни с одним набором
выше, до `MATCH` не дойдёт, сколько наборов ни скачай. Поэтому в работу входят
обе стены.

размер файла более чем вдвое». Всё, что написано ниже про формат и про семантику
совпадения, прочитано в исходниках `MetaCubeX/mihomo`, ветка `Alpha`, и здесь
перечислено поимённо — чтобы при расхождении было понятно, что перепроверять.

Формат подтверждён и эмпирически: у всех 23 файлов `.mrs`, скачанных из живого
конфига, магия и байт behavior сошлись с прочитанным.

## Что уже сделано до этой спеки

Коммит `8adf32e` — трассировка учитывает модификатор `no-resolve`. Правило по IP
(`IP-CIDR`, `IP-CIDR6`, `GEOIP`, а также `RULE-SET` при `behavior: ipcidr`),
которому запрещён резолв, при цели без IP даёт определённое «не совпало», а не
остановку. Это сдвинуло проход в разбираемом конфиге с правила #1 на #4 и не
требует ни загрузки, ни сети: `behavior` берётся из самого документа.

Отсюда следует важное для спеки: **набор с `behavior: ipcidr` и `no-resolve` при
цели-домене скачивать не нужно вовсе** — ответ известен заранее. Загрузка нужна
там, где ответ зависит от содержимого.

## Границы

**Делаем:**

- загрузку наборов вида `type: http` по ссылке из документа, с кэшем на диске;
- разбор всех трёх форматов: `mrs`, `yaml`, `text`;
- разбор всех трёх поведений: `domain`, `ipcidr`, `classical`;
- наборы `type: inline` — содержимое лежит в самом документе, сеть не нужна;
- ответы в трассировку с отдельным состоянием «недоступен» и причиной;
- необязательное поле «процесс» в цели трассировки — вторая стена из раздела
  «Цель»;
- диалог состояния наборов с просмотрщиком содержимого;
- ограничение размера в `net/guard.ts` — сегодня его нет ни у наборов, ни у
  geo-баз.

**Не делаем:**

- наборы `type: file` — путь указывает на файловую систему клиента, у сервера
  такого файла нет и быть не может. Честный ответ — «недоступен» с этой
  причиной, а не попытка угадать;
- загрузку через прокси, указанный в поле `proxy` провайдера. Редактор ходит
  напрямую. Если набор доступен только через прокси, у нас он не загрузится, а
  у клиента загрузится — это расхождение выносим в оговорку, а не прячем;
- редактирование содержимого наборов: они принадлежат чужим репозиториям;
- влияние на сохранение шаблона. Недоступный набор не блокирует кнопку: ни
  панель, ни клиент от нашей неспособности его скачать не зависят.

## Формат `.mrs`

Весь файл — один zstd-поток. Внутри, в порядке чтения:

```
magic     4 байта   'M','R','S',1
behavior  1 байт    0 = domain, 1 = ipcidr, 2 = classical
count     int64 BE  число записей
extraLen  int64 BE  зарезервировано; сейчас всегда 0
extra     extraLen байт
тело      по behavior
```

Тело для `domain` (`ReadDomainSetBin`):

```
version      1 байт    обязан быть 1
len(leaves)  int64 BE, затем столько же uint64 BE
len(bitmap)  int64 BE, затем столько же uint64 BE
len(labels)  int64 BE, затем столько же байт
```

Тело для `ipcidr` (`ReadIpCidrSet`):

```
version  1 байт    обязан быть 1
len(rr)  int64 BE, затем пары по 16 байт: начало и конец диапазона (As16)
```

Формат `classical` внутри `.mrs` не встречается: вики ядра прямо пишет, что
`mrs` поддерживает только `domain` и `ipcidr`. Байт behavior = 2 обрабатываем
как неподдержанный, а не как ошибку разбора.

### Поиск в наборе доменов

Внутри лежит сжатый префиксный бор (succinct trie): два битовых массива и массив
меток. Ключи хранятся **перевёрнутыми** (`utils.Reverse`), поэтому поиск идёт по
ключу с конца; сравнение приводит ASCII к нижнему регистру. Поддержаны две
подстановки: `*` заменяет одну метку (между точками) и требует отката по стеку,
`+` совпадает со всем остатком и завершает поиск успехом немедленно.

`ranks` и `selects` в структуре — предвычисленные ускорители операций rank и
select. На ответ они не влияют: наивные реализации дают тот же результат.
Портируем `Has` построчно, ускорители заменяем префиксными суммами.

Порт делаем именно построчным. Это чужой алгоритм с нетривиальным откатом; его
пересказ своими словами — самый вероятный источник неверного ответа во всей
работе, а неверный ответ здесь хуже отказа: он выглядит как знание.

## Контракт бэкенда

Дескриптор шлёт фронтенд: только он читает документ. Ссылку проверяет бэкенд —
`assertPublicHost` на каждом хопе редиректа, как у geo.

```ts
interface RuleSetDescriptor {
  name: string
  kind: 'http' | 'inline'
  url?: string          // kind === 'http'
  payload?: string[]    // kind === 'inline'
  behavior: 'domain' | 'ipcidr' | 'classical'
  format: 'mrs' | 'yaml' | 'text'   // пустое поле документа означает yaml
}
```

`POST /api/tools/ruleset/match` — на вход `{ target: { address, ip? }, sets: RuleSetDescriptor[] }`:

```ts
type RuleSetAnswer =
  | { state: 'yes' | 'no'; count: number }
  | { state: 'lines'; lines: string[]; count: number }   // behavior === 'classical'
  | { state: 'unavailable'; reason: string }

interface RuleSetMatchResult {
  answers: Record<string, RuleSetAnswer>
}
```

`POST /api/tools/ruleset/status` — состояние кэша по списку дескрипторов (для
диалога). Метод POST, а не GET: дескрипторов до 64, и в строке запроса им не
поместиться. `POST /api/tools/ruleset/refresh` — принудительная перезагрузка
одной ссылки или всех. `POST /api/tools/ruleset/page` — постраничная выдача
содержимого для просмотрщика: `{ descriptor, offset, limit, q? }` →
`{ total, offset, items }`.

Состояние `unavailable` обязательно и несёт причину. Недоступный набор
обязан оставить трассировку остановленной; превратить его в «не совпало» значило
бы дать уверенный неверный ответ — ровно то, ради запрета чего в этой
трассировке заведена остановка.

## Разделение труда

Ответ считает тот, у кого есть инструмент.

- `domain` и `ipcidr` — считает **бэкенд**: только у него декодер бора и
  диапазонов, и гонять 300 тысяч диапазонов на клиент бессмысленно.
- `classical` — бэкенд отдаёт **строки**, считает **фронтенд**: строки там суть
  полноценные правила Mihomo, а единственный их вычислитель живёт в
  `entities/mihomo/trace.ts`. Второй копии вычислителя в проекте не будет.

Ядро для `classical` возвращает ИЛИ по правилам набора
(`classical_strategy.go`), и наш вычислитель обязан вести себя так же:
непроверяемое условие в строке даёт по набору «неизвестно» с указанием строки, а
не «не совпало». `MATCH`, `RULE-SET` и `SUB-RULE` внутри `classical` ядро
отвергает при разборе — такую строку считаем испорченной и говорим об этом, а не
пытаемся вычислить.

## Кэш и лимиты

Числа получены измерением, а не назначены. Скачаны и разобраны все 26 наборов из
живого конфига плюс самые тяжёлые ходовые наборы экосистемы.

**Живой конфиг, 26 наборов:** 135 КБ на проводе, 540 КБ после распаковки, 18 303
записи. Самый тяжёлый — 93 КБ → 485 КБ (15 511 подсетей). Все наборы доменов в
нём меньше 6 КБ.

**Тяжёлый конец экосистемы** (`MetaCubeX/meta-rules-dat`):

| Набор | На проводе | Распаковано | Записей |
|---|---|---|---|
| `geoip/us.mrs` | 586 КБ | 3 142 КБ | 300 531 |
| `geosite/cn.mrs` | 526 КБ | 884 КБ | 111 004 |
| `geosite/geolocation-!cn.mrs` | 193 КБ | 315 КБ | 27 041 |
| `geoip/cn.mrs` | 37 КБ | 207 КБ | 9 622 |

Закономерность: наборы доменов почти всегда мелкие, пухнут наборы подсетей для
крупных стран. Потолок реального мира — около 0.5 МБ на проводе и 3 МБ после
распаковки. Худшее наблюдаемое раздутие zstd на настоящих данных — ×5.6.

**Лимит на размер, скачанный с провода, при этом не защищает ни от чего.**
Проверено: 64 МБ нулей сжимаются zstd в 2067 байт — раздутие ×32 000.
Единственный работающий предохранитель — предел на выходе распаковщика, и в Node
он есть: `zstdDecompressSync(buf, { maxOutputLength })` бросает
`ERR_BUFFER_TOO_LARGE` на пороге, не дав аллокации случиться.

| Лимит | Значение | Обоснование |
|---|---|---|
| Файл на проводе | 8 МБ | ×14 от самого тяжёлого измеренного (586 КБ) |
| После распаковки | 32 МБ, через `maxOutputLength` | ×10 от 3.1 МБ; единственная настоящая защита |
| Наборов на документ | 64 | ×2.5 от измеренных 26 |
| Кэш на диске | 256 МБ, вытеснение по давности обращения | 64 набора по 586 КБ ≈ 37 МБ на самый тяжёлый мыслимый документ |
| Разобранное в памяти | LRU по объёму, 64 МБ | `geoip/us` в разборе ≈ 10 МБ |
| Строк `classical` в ответе | 10 000 | ×33 от измеренного максимума (303) |
| TTL | `interval` из документа, но не чаще раза в час | документ просит 86400 и 2592000 |

Каждый предел при срабатывании даёт по набору `unavailable` с текстом про
конкретный предел, а не общий отказ на весь запрос: документ с 65 наборами
обязан ответить по первым 64 и честно сказать про остальные. Отказ целиком
превратил бы превышение в неработающую трассировку вместо частичной.

Кэш лежит в `DATA_DIR/rulesets/<sha256 от ссылки>` — имя файла из хэша, а не из
ссылки: в ссылке бывает что угодно, включая `..`.

Ограничение размера добавляется параметром `maxBytes` в `fetchExternal`
(`net/guard.ts`), а не отдельной обвязкой в наборах: сегодня без предела качает и
geo, и это чинит оба места разом.

Разбор всегда идёт в отдельной попытке с ловлей исключений. Битый файл обязан
дать `unavailable`, а не 500: кнопку «проверить» жмут именно тогда, когда с
документом что-то не так.

## Что меняется в трассировке

`traceMihomo(md, target, geo, ruleSets)` — четвёртый аргумент. `RULE-SET`
перестаёт быть безусловной остановкой и разбирается по порядку:

1. `no-resolve` при `behavior: ipcidr` и цели без IP — «не совпало», сеть не
   нужна (уже сделано в `8adf32e`);
2. есть ответ `yes`/`no` — вердикт правила;
3. `classical` — вычисляем строки нашим же вычислителем условий;
4. ответа нет — остановка с конкретной причиной: «404», «формат не
   поддерживается», «набор ещё загружается», «набор лежит в файле клиента»,
   «размер превысил предел».

Формулировка причины входит в контракт: нынешнее «редактор его не скачивает»
станет неправдой, и оставлять её нельзя.

Оговорки трассы пополняются двумя. Первая — про прокси: если у провайдера задано
поле `proxy`, клиент скачает набор через него, а редактор ходил напрямую, и
содержимое могло отличаться. Вторая — про давность: набор из кэша может быть
старее того, что скачает клиент.

## Правила по процессу

Вторая стена. Сегодня все шесть типов `PROCESS-*` лежат в `NO_DATA_TYPES` и
останавливают проход, потому что в цели трассировки нет процесса. Заводим его
тем же способом, каким в цели уже живёт необязательный «IP назначения»: пусто —
остановка как сейчас, заполнено — правило становится проверяемым.

Поле в строке трассировки **одно**, а метаданных у ядра два — `Process` (имя) и
`ProcessPath` (путь), и они разные (`rules/common/process.go`). Разводим их по
введённому значению:

- значение содержит `/` или `\` — это путь: `PROCESS-PATH*` сравнивают с ним
  целиком, `PROCESS-NAME*` — с последним сегментом;
- разделителей нет — это имя: `PROCESS-NAME*` сравнивают с ним, а `PROCESS-PATH*`
  **остаются остановкой**. Путь из имени не выводится, и подставлять сюда догадку
  значило бы соврать.

Семантика сравнения взята из `rules/common/process.go` и
`component/wildcard/wildcard.go`, а не из документации:

| Тип | Как сравнивает ядро |
|---|---|
| `PROCESS-NAME`, `PROCESS-PATH` | `strings.EqualFold` — совпадение целиком, без учёта регистра |
| `PROCESS-NAME-WILDCARD`, `PROCESS-PATH-WILDCARD` | `wildcard.Match`, обе стороны в нижнем регистре: `*` — ноль и больше символов, `?` — ровно один, совпадение целиком |
| `PROCESS-NAME-REGEX`, `PROCESS-PATH-REGEX` | `regexp2` с флагом `IgnoreCase` и `MatchString` — **поиск подстроки**, а не совпадение целиком |

Две вещи здесь легко сделать неверно, и обе стоят отдельного теста.
Во-первых, `-REGEX` не заякорен: `PROCESS-NAME-REGEX,discord` ловит и
`Discord.exe`, и `my-discord-helper.exe`. Во-вторых, движок там `regexp2`
(.NET-совместимый), а не RE2 — по возможностям он ближе к `RegExp` браузера, чем
гошный, но совпадение не полное. Выражение, которое `RegExp` не компилирует, даёт
«неизвестно» с причиной — тем же способом, что уже сделано для `DOMAIN-REGEX`, а
не молчаливым промахом.

`PROCESS-*` уходят из `NO_DATA_TYPES` не списком в коде: множество выводится из
`RULE_TYPES` вычитанием, и таким оно и остаётся. Проверяемость решается наличием
значения в цели, а не принадлежностью к списку.

Набор `behavior: classical` из строк `PROCESS-NAME` (правило #25 эталонного
шаблона) считается тем же вычислителем и по тем же правилам — отдельной ветки
для него нет.

## UI

**Диалог «Наборы правил»** — кнопка в топбаре редактора Mihomo, рядом с
«Geo-базы». Строка на провайдера: имя, `behavior`/`format`, состояние (загружен /
ошибка с текстом / формат не поддержан / только у клиента), число записей,
размер, когда загружен, кнопка «Обновить». Сверху — «Обновить все».

Провайдеры, которых редактор загрузить не может в принципе (`type: file`),
показываются с этой причиной, а не прячутся: их отсутствие в списке читалось бы
как «в документе их нет».

**Просмотрщик содержимого** открывается кликом по строке: постраничный список
записей с поиском, как `GeoBrowser` для geo-баз. Для `domain` — домены (обход
бора `Foreach`, ключи в нём лежат перевёрнутыми), для `ipcidr` — подсети
(обратное превращение диапазонов в CIDR), для `classical` — строки правил.

Это самая дорогая часть работы и единственная, которую можно отложить, не ломая
остального: трассировке просмотрщик не нужен.

**Строка трассировки** получает необязательное поле «процесс» рядом с «IP
назначения». `TraceBar` общий у обоих редакторов, а правил по процессу у Xray
нет — поле включается пропом со стороны `MihomoEditorPage`, а не показывается
всем. Плейсхолдер подсказывает оба принимаемых вида: `chrome.exe` и
`C:\Program Files\...\chrome.exe`.

**Панель разбора трассы**: у правила `RULE-SET` показываем, что ответ получен из
загруженного набора и сколько в нём записей — иначе «не совпало» по набору из ста
тысяч доменов неотличимо от «не совпало» по пустому.

## Диагностика

Недоступный или битый набор становится **предупреждением** в общем списке
диагностик шаблона, а не ошибкой: документ от этого не перестаёт быть
корректным, и клиент его загрузит. По той же причине сохранение не блокируется.

Существующая проверка «`RULE-SET` ссылается на провайдера, которого нет в
документе» (`validate.ts:168`) остаётся как есть — она про документ, а не про
сеть.

## Тестирование

Три опоры, и первая обязательна.

1. **Настоящие бинарные фикстуры.** Берём самые маленькие из измеренных:
   `escapefromtarkov.mrs` (4 записи), `faceit.mrs` (2), geoip `private.mrs` (17).
   Вместе меньше килобайта. Это единственная проверка того, что наш декодер не
   разошёлся с ядром, и она нужна ровно потому, что всё остальное мы пишем сами.
2. **Порт строителя `NewDomainSet` в тестовый хелпер.** Нужен, чтобы собирать
   наборы с подстановками `*` и `+` и проверять на них поиск: сгенерировать
   `.mrs` нам нечем, ядра в CI нет. Строитель живёт только в тестах.
3. **Отказы.** Чужая магия, чужая версия, байт behavior не тот, обрыв потока,
   404, таймаут, zstd-бомба, превышение предела распаковки, `type: file` —
   каждый обязан дать `unavailable` с причиной, а не исключение и не «не
   совпало».

Риск второй опоры назван прямо: строитель и читатель, написанные одной рукой,
могут ошибаться одинаково и покрыть друг друга. Поэтому первая опора
обязательна — она сверяет нас с настоящим ядром.

Трассировка проверяется на документе с наборами всех трёх поведений: ответ `yes`
ведёт в цель правила, `no` пропускает дальше, `unavailable` останавливает с
причиной.

Правила по процессу получают свои случаи: точное сравнение без учёта регистра;
подстановки `*` и `?`; **незаякоренный** `-REGEX` (`discord` обязан поймать
`my-discord-helper.exe` — тест, который поймает ошибочное якорение); путь против
имени (введён путь — работают оба семейства, введено имя — `PROCESS-PATH*`
остаются остановкой); пустое поле — остановка как сегодня.

Приёмочный тест один и сквозной: эталонный `roscomvpn-mihomo-ru.yaml` лежит
фикстурой, наборы отвечают из подменённого сервиса, процесс задан — проход
обязан дойти до правила #31. Он же ловит обратную ошибку: если какая-то ветка
начнёт врать «не совпало» вместо остановки, победитель окажется не тот.

Ни один тест не ходит в сеть: фикстуры лежат в репозитории, загрузка
подменяется, как в тестах geo.

## Риски

**Формат сменится.** `MRS1` — версия в магии, плюс байт версии внутри тела. Обе
проверяем; незнакомое значение даёт `unavailable` с текстом про версию.
Деградация при этом ровно в нынешнее поведение — остановку прохода, а не в
неверный ответ.

**Порт `Has` разойдётся с ядром на подстановках.** Самая тонкая часть работы.
Митигация — построчный порт плюс обе первые опоры тестирования.

**Медленный первый запрос.** Документ с 26 наборами при пустом кэше — 26
загрузок. Идут параллельно с общим пределом одновременности; трассировка
показывает «загружается» и пересчитывается по готовности, а не блокирует UI.

## Порядок работ

Два плана, граница проходит по «работает без UI».

**План 1 — ядро.** `net/guard.ts` (`maxBytes`), декодеры
`mrs`/`domainSet`/`ipcidrSet`/`payload`, кэш, `RuleSetService`, роут `match`,
дескрипторы провайдеров на фронтенде, приём ответов в трассировке, вычисление
`classical`, поле «процесс» в цели трассировки вместе с шестью типами
`PROCESS-*`, оговорки.

Приёмка плана 1 проверяемая и одна: на эталонном шаблоне
`roscomvpn-mihomo-ru.yaml` цель, не совпавшая ни с одним набором, доходит до
правила #31 (`MATCH,PROXY`), а не встаёт на #4 или #25. Обе стены из раздела
«Цель» входят в план 1 именно поэтому: любая из них поодиночке оставляет проход
остановленным, и половина работы не даёт половины результата.

**План 2 — UI.** Роуты `status`/`refresh`/`page`, диалог «Наборы правил»,
просмотрщик содержимого, пометки в панели разбора трассы, диагностика,
документация в README и CLAUDE.md.

## За рамками

Наборы правил sing-box (`rule_set` с `format: binary` — это другой формат, свой
у SagerNet), загрузка через прокси провайдера, редактирование наборов,
собственный конвертер `yaml` → `mrs`.
