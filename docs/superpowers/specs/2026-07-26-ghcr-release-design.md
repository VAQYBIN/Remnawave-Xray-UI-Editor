# Публикация образа в ghcr.io и релизный конвейер — дизайн

Готовый мультиарх-образ в GitHub Container Registry, автоматические версии и релизы из
conventional-коммитов, установка проекта двумя скачанными файлами вместо `git clone` и сборки
на машине пользователя.

## Задача

Сегодня установка выглядит так: клонировать репозиторий, скопировать `.env.example`, выдать
права на `./data` командой с `sudo chown`, собрать образ у себя. Это значит, что на VPS
пользователя оказываются исходники, Node, npm и полный цикл сборки фронтенда — ради
приложения, которое ему нужно только запустить. Плюс два места, где первый запуск ломается:
забытый `chown` (тот самый `EACCES: permission denied, mkdir 'data'`, на который наткнулся
смок-тест прод-образа) и любая ошибка сборки, которую он увидит как стену чужих логов.

Одновременно репозиторий не проверяет `Dockerfile` вообще: `ci.yml` гоняет типы, юниты, e2e и
gitleaks, но прод-образ не собирается ни разу. Поломка всплывёт у первого, кто попробует
поставить.

## Решение целиком

```
push в main
  ├─ job release-please  → есть ли релизные коммиты?
  │     нет  → обновляет/создаёт PR «chore: release 1.1.0», выходит
  │     да   → создаёт тег v1.1.0 + GitHub Release с notes,
  │            отдаёт наружу release_created / version / major / minor
  ├─ job build (amd64, ubuntu-latest)     ─┐
  ├─ job build (arm64, ubuntu-24.04-arm)  ─┤ push по дайджесту, без тегов
  └─ job merge                            ←┘ склеивает манифест и вешает теги:
        всегда:            :edge, :sha-<короткий>
        если был релиз:    :1.1.0, :1.1, :1, :latest
```

Единственное событие — push в `main`. Тег не триггер, а результат.

## Почему не `on: push: tags`

Очевидная схема «бот ставит тег → workflow на теге собирает образ» не работает, и это надо
зафиксировать, чтобы никто не переизобрёл её позже.

`main` защищён ruleset'ом с **пустым списком bypass**. Отсюда два следствия:

1. Автоматика не может пушить в `main` — бамп версии обязан приезжать через PR.
2. **События, порождённые `GITHUB_TOKEN`, не запускают workflow'ы** (защита GitHub от
   рекурсии). Значит, тег от бота не запустил бы публикацию, а на релизном PR не появилось бы
   ни одной проверки — и required checks не дали бы его смержить.

Обход: релизным PR управляет fine-grained PAT (события от него — от человека, проверки
запускаются), а публикация образа живёт в том же прогоне, который создал тег, и триггер ей не
нужен.

## Реестр и имя

`ghcr.io/vaqybin/remnawave-xray-ui-editor` — GHCR принимает только нижний регистр, а
`github.repository` даёт `VAQYBIN/Remnawave-Xray-UI-Editor`. Имя пишется в workflow литералом,
а не через контекст: явная строка не сломается от переименования регистра.

| Тег | Когда | Кому |
| --- | --- | --- |
| `:latest` | релиз | `docker-compose.yml` по умолчанию |
| `:1.2.3`, `:1.2`, `:1` | релиз | закрепиться на версии |
| `:edge` | каждый push в main | попробовать невыпущенное |
| `:sha-6643561` | каждый push в main | точный откат, отладка |

К образу прикладываются метка `org.opencontainers.image.source` (связывает пакет с
репозиторием и даёт на его странице ссылку на исходники), SBOM и provenance-аттестация.
Аттестация вешается на дайджест **манифеста-индекса**, а не на дайджесты отдельных платформ,
иначе `gh attestation verify` по тегу не найдёт её.

Проверка потребителем — без установки чего-либо, кроме `gh`:

```bash
gh attestation verify oci://ghcr.io/vaqybin/remnawave-xray-ui-editor:latest \
  --repo VAQYBIN/Remnawave-Xray-UI-Editor
```

Cosign рассмотрен и **сознательно не добавлен**: он стоит на той же инфраструктуре Sigstore и
утверждает то же самое, а вторая подпись нужна лишь тем, у кого `cosign verify` уже встроен в
admission-контроллер Kubernetes. У проекта, который ставят одной командой на VPS, такого
потребителя нет.

## Две архитектуры

Выбраны нативные раннеры, а не QEMU: публичным репозиториям GitHub даёт arm64-раннеры
бесплатно, а под эмуляцией `vite build` и `tsc` растянули бы каждый релиз с ~5 минут до 20+.

Каждый build-джоб пушит **по дайджесту** (`push-by-digest`, без тегов) и отдаёт дайджест
артефактом; `merge` собирает из них один манифест через `buildx imagetools create` и только
там навешивает теги. Это стандартный приём распределённой мультиарх-сборки: теги появляются
один раз и атомарно, промежуточных состояний, где `:latest` указывает на половину платформ,
не существует.

### Изменения в `Dockerfile`

Меняется ровно один слой — тот, что качает ядро:

```dockerfile
FROM alpine:3.24 AS xray
ARG TARGETARCH                     # подставляет buildx
ARG XRAY_VERSION=v26.6.27
ARG XRAY_SHA256_AMD64=b3e5902d06d6282fe53cfa2fc426058b9aeaa429b2c812e20887cd47f26d08bf
ARG XRAY_SHA256_ARM64=…            # из Xray-linux-arm64-v8a.zip.dgst того же релиза
```

`amd64` → `Xray-linux-64.zip`, `arm64` → `Xray-linux-arm64-v8a.zip`; sha256 выбирается по той
же переменной. Проверка контрольной суммы сохраняется для обеих архитектур — она здесь и есть
защита от подмены ядра.

Второе изменение, в финальном слое:

```dockerfile
RUN mkdir -p /data && chown node:node /data
```

Docker копирует владельца каталога из образа в свежий именованный том — благодаря этой строке
`chown 1000:1000` из инструкции исчезает совсем.

`XRAY_SHA256_ARM64` нельзя выдумать: он берётся из файла `.dgst` релиза v26.6.27 при
реализации и сверяется с фактически скачанным архивом первой же сборкой.

## Compose и установка

`docker-compose.yml` становится файлом для пользователя: `image:` вместо `build:`, именованный
том `xray-editor-data` вместо bind-mount. Сборка из исходников уезжает в
`docker-compose.build.yml` — тот же сервис, но `build: .` и bind-mount `./data`, потому что
разработчику удобнее видеть бэкапы обычным `ls`.

Установка сводится к четырём строкам:

```bash
curl -fsSLO https://raw.githubusercontent.com/VAQYBIN/Remnawave-Xray-UI-Editor/main/docker-compose.yml
curl -fsSL -o .env https://raw.githubusercontent.com/VAQYBIN/Remnawave-Xray-UI-Editor/main/.env.example
nano .env                # панель, токен, пароль, секрет сессии
docker compose up -d
```

Ни `git clone`, ни `chown`, ни `--build`. Блок `> [!IMPORTANT]` про uid 1000 удаляется
целиком: он перестаёт быть правдой, а устаревшее предупреждение вреднее отсутствующего.

Порядок переменных остаётся рабочим: Compose читает `.env` и для подстановки `${PORT}`, и как
`env_file` контейнера, а `environment:` (где заданы `DATA_DIR`, `STATIC_DIR`, внутренний
`PORT`) имеет приоритет над `env_file` — то есть пользователь не сломает пути, правя `.env`.

Цена именованного тома: файлы бэкапов больше не лежат рядом в `./data`. Достаются через
`docker compose cp`, но штатный способ смотреть и восстанавливать их — диалог «Версии» в самом
редакторе, и он удобнее в любом случае.

## Проверка `Dockerfile` на PR

В `ci.yml` добавляется джоб `docker`: собирает **только amd64 и без пуша**, с кэшем GHA. Идёт
параллельно остальным джобам, поэтому на общее время PR почти не влияет. Смысл — узнавать о
поломке образа на PR, а не в момент релиза.

Джоб ограничен событием `pull_request` (`if: github.event_name == 'pull_request'`): на push в
`main` ту же сборку делает `release.yml`, и дублировать её незачем.

Джоб живёт именно в `ci.yml`, а публикация — в отдельном `release.yml`. Разделение
принципиальное: `ci.yml` запускают PR из форков, и он обязан оставаться с
`permissions: contents: read`; публикация требует `packages: write`. Один файл на оба режима
означал бы права записи в реестр в прогоне, инициированном чужим кодом.

## Версии и релизы

Release Please читает conventional-коммиты (проект уже пишет их: `fix(frontend): …`) и держит
открытым PR «chore: release X.Y.Z», в котором лежат обновлённый `CHANGELOG.md` и `version` в
корневом `package.json`. Будущий релиз виден целиком до выпуска и правится руками прямо в этом
PR; выпуск — мерж.

Конфигурация: `release-please-config.json` (`release-type: node`, только корневой пакет —
`backend/package.json` и `frontend/package.json` не версионируются, наружу они не публикуются)
и `.release-please-manifest.json`.

Три частности:

- **Первая версия — 1.0.0.** Проект функционально завершён и работает в проде; до единицы
  semver формально разрешает ломать совместимость каждым релизом, и тег `:1` теряет смысл.
  Требует одноразового `"release-as": "1.0.0"` в конфиге — иначе бот пойдёт от нуля и
  предложит `0.1.0`. После первого релиза строка убирается отдельным коммитом.
- **`CHANGELOG.md` будет английским**: он собирается из тем коммитов, а они по конвенции
  проекта английские. Русский README и английский CHANGELOG честнее машинного перевода тем
  коммитов.
- **Релиз не ждёт CI, и это осознанно.** Включено «Require branches to be up to date before
  merging», то есть в `main` попадает ровно то дерево, на котором проверки уже прошли зелёными.
  Второй прогон только задержал бы публикацию.

## Документация

- README: новый быстрый старт (выше), обновление (`docker compose pull && docker compose up -d`),
  доступ к бэкапам через `docker compose cp`, сборка из исходников в «Разработке», порядок
  выпуска релиза там же.
- Живой бейдж версии `shields.io/github/v/release` — не требует правки при каждом выпуске.
- `.env.example` не меняется: состав переменных прежний, а его содержимое теперь скачивают
  напрямую по ссылке на `main` — то есть файл стал частью установки и должен оставаться
  копируемым как есть.

## Что выставляется руками

Файлы — в этом плане; переключатели — за владельцем репозитория, как и с базовой
безопасностью:

1. **Fine-grained PAT** на этот репозиторий (Contents: RW, Pull requests: RW) в секрете
   `RELEASE_PLEASE_TOKEN`. Форкам он недоступен: `release.yml` запускается только на push в
   `main`.
2. **Сделать пакет публичным** после первого релиза. GHCR создаёт новый пакет приватным, и
   `docker pull` будет требовать логина, пока видимость не переключена.
3. **Связать пакет с репозиторием** (Manage Actions access) — чтобы репозиторий мог
   перезаписывать его без PAT.
4. Опционально — добавить `docker (build only)` в required checks ruleset'а.

## Проверка

- Локально: `docker buildx build --platform linux/arm64` (через встроенную эмуляцию, один раз
  и медленно) — убедиться, что в образ попало ядро правильной архитектуры; затем запуск нового
  `docker-compose.yml` с пустым томом, чтобы увидеть, что `EACCES` действительно исчез.
- В CI: зелёный релизный прогон и `docker manifest inspect` — две платформы в одном манифесте.
- `gh attestation verify` по опубликованному тегу.

## Вне рамок

- Подпись cosign — обоснование выше.
- Публикация npm-пакетов: workspace'ы наружу не выкладываются.
- Автообновление образа на серверах пользователей (watchtower и подобное) — решение
  пользователя, не проекта.
