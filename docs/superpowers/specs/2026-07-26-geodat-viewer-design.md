# GeoDat Viewer — дизайн

Просмотр geo-баз из редактора: какие категории есть в `geosite.dat` и `geoip.dat`, что лежит
внутри каждой, и как перенести нужную категорию в правило маршрутизации.

## Задача

Сейчас geo-базы — чёрный ящик. Пользователь пишет в правиле `geosite:netflix`, а совпадает ли
там нужный домен и существует ли вообще такая категория, показывает только трассировщик — по
одному адресу за раз. Вьюер отвечает на два вопроса напрямую: «какие категории есть» и «что
внутри этой категории».

Вьюер — не отдельный справочник, а часть рабочего потока: найденная категория одной кнопкой
уходит в правило редактируемого конфига.

## Что уже есть

`GeoService` (`backend/src/geo/service.ts`) держит в памяти индекс `код → сырые байты записи`
(`indexEntries` из `dat.ts`) и лениво разбирает нужные категории (`domainsOf` / `cidrsOf`),
кэшируя результат до смены mtime файла. Значит список категорий доступен бесплатно
(`index.keys()`), а содержимое — уже написанным разбором. Не хватает трёх вещей: счётчиков,
пагинации и сериализации наружу.

## Бэкенд

### Ручки

```
GET /api/geo/:kind/categories
    → { categories: [{ code: string, count: number }] }

GET /api/geo/:kind/categories/:code?q=&offset=&limit=
    → geosite: { code, total, items: [{ type, value, attributes }] }
      geoip:   { code, total, reverseMatch, items: [{ cidr }] }
```

`kind` — `geosite` или `geoip`, проверяется zod'ом. `type` домена сериализуется словом:
`keyword` (0), `regexp` (1), `domain` (2), `full` (3) — цифры из geodat.proto наружу не уходят.
CIDR отдаётся строкой `1.2.3.0/24` (IPv6 — в сжатой форме).

`limit` по умолчанию 200, максимум 1000; `offset` — от нуля. `q` фильтрует по подстроке
значения без учёта регистра, и `total` считается уже после фильтра — иначе пагинация врёт.

Категории в ответе отсортированы по коду: порядок в `.dat` произвольный, а список должен быть
стабильным между запросами.

### Счётчики без полного разбора

Список категорий показывает размер каждой. Полный разбор всех категорий ради этого недопустим:
в geosite их 1520, а `US` в geoip — 291 507 подсетей, и разбор всей базы в объекты — это сотни
мегабайт. Поэтому в `dat.ts` появляется `countEntries(entry): number` — проход по байтам записи
со счётом тегов поля 2 (`domain` у GeoSite, `cidr` у GeoIP) без декодирования строк и создания
объектов. Результат кэшируется рядом с индексом, одной картой `code → count`.

### Предел кэша разобранных категорий

`GeoService` кэширует разобранные категории без ограничений. До сих пор это было безопасно:
туда попадали только категории из редактируемого конфига — две-три штуки. Вьюер меняет профиль
нагрузки: пользователь листает категории подряд, и `US` рядом с `CN` — это уже сотни мегабайт
живых объектов.

Поэтому кэш разобранного получает предел: не больше 8 категорий на каждый вид, при переполнении
вытесняется самая старая по времени добавления. Индекс и счётчики кэшируются как раньше — они
лёгкие и нужны постоянно.

### Ошибки

Базы нет на диске — 404 `«База geosite не загружена — скачайте её на вкладке „Источники“»`.
Нет такой категории — 404 `«В базе geosite нет категории „NOSUCH“»`. Это разные ситуации, и
пустой список вместо ошибки скрыл бы обе.

## Фронт

### Раскладка

`GeoDataDialog` получает две вкладки: **«Источники»** (нынешнее содержимое — ссылки, статус,
кнопка обновления) и **«Просмотр»**. Кнопка в топбаре остаётся одна.

Вкладка «Просмотр» — новый компонент `features/diagnostics/GeoBrowser.tsx`:

```
┌─ Geo-базы ──────────────────────────────────────────┐
│ [Источники][Просмотр]                               │
│ (geosite|geoip)   Поиск категории: [goog        ]   │
│ ┌────────────────┬────────────────────────────────┐ │
│ │ GOOGLE     960 │ Поиск: [api            ]       │ │
│ │ GOOGLE-CN   12 │ full     googleapis.com        │ │
│ │ GOOGLEFCM    4 │ domain   google.com  @cn       │ │
│ │ …             │ показаны 1–200 из 960  [←][→]  │ │
│ └────────────────┴────────────────────────────────┘ │
│                     [Скопировать geosite:google]    │
│                     [В правило]                     │
└─────────────────────────────────────────────────────┘
```

Список категорий фильтруется по подстроке кода на клиенте (весь список — это ~40 КБ, один
запрос) и рисуется не больше чем на 300 строк: 1520 узлов в DOM делают диалог заметно вязким.
Когда список обрезан, под ним подпись «показаны первые 300 — уточните поиск».

Содержимое категории приходит постранично: своё поле поиска, счётчик «показаны N–M из K» и
кнопки листания. Каждый домен помечен типом (`full`, `domain`, `keyword`, `regexp`) и своими
атрибутами (`@cn`, `@ads`) — без этого «google.com» и «keyword google» выглядят одинаково, хотя
матчатся совершенно по-разному.

Базы нет — вместо таблиц сообщение и кнопка, переключающая на вкладку «Источники».

### Данные

Два хука в `shared/api/hooks.ts`: `useGeoCategories(kind, enabled)` (кэшируется, `staleTime`
минута — база на диске не меняется сама) и `useGeoCategory(kind, code, { q, offset })`. Ввод в
оба поля поиска проходит через существующий `useDebounced` (600 мс) — фильтр категорий локальный,
но поиск внутри категории бьёт в бэкенд на каждый символ без него.

### Вставка в конфиг

«Скопировать» кладёт `geosite:google` в буфер обмена. «В правило» пишет в черновик через новую
чистую функцию в `entities/graph/mutations.ts`:

```ts
appendGeoKey(config: XrayConfig, ruleIndex: number | null, key: string): { config, ruleIndex }
```

`geosite:*` дописывается в `rule.domain`, `geoip:*` — в `rule.ip`; повтор не добавляется
(возвращается тот же конфиг, как у прочих мутаций). При `ruleIndex === null` создаётся новое
правило в конце списка — там же, где его создаёт кнопка «+ Правило», чтобы поведение не
раздваивалось. Возвращённый `ruleIndex` нужен вызывающему, чтобы выбрать правило в инспекторе.

`EditorPage` передаёт индекс выбранного правила, если открыт инспектор правила, иначе `null`.
После вставки диалог закрывается и правило выделяется — пользователь сразу видит, куда попала
категория.

Ключ пишется в нижнем регистре (`geosite:google`), хотя в базе код лежит как `GOOGLE`: так
принято в конфигах Xray, а `parseKey` в `geo/match.ts` апперкейсит код при разборе — трассировка
и проверка ядром такой ключ найдут.

## Тестирование

**Бэкенд.** `countEntries` на существующих фикстурах `geo-dat.test.ts`, включая категорию без
записей. Страницы содержимого: границы `offset`/`limit` (последняя страница, `offset` за концом,
`limit` выше максимума), фильтр `q` и пересчёт `total`, `reverseMatch` у geoip, сортировка
категорий. Ручки: 404 при отсутствии базы и при неизвестном коде, отказ на неизвестном `kind`.
Вытеснение кэша: после перебора девяти категорий в памяти остаются восемь.

**Фронт.** `appendGeoKey` — вставка в выбранное правило, создание нового, отказ от дубликата,
geoip в `ip`. Компонентный тест `GeoBrowser`: список с счётчиками, фильтр категорий, листание
страниц, «В правило» отдаёт наверх ожидаемый ключ, сообщение при незагруженной базе.

**E2E.** «Geo-базы» → «Просмотр» → выбрать категорию → «В правило» → на графе появился узел
правила и черновик помечен изменённым. Новые ручки добавляются в `e2e/mocks.ts`.

## Что осознанно не делаем

- **Обратный поиск «в каких категориях есть домен X»** — требует перебора всех категорий с их
  полным разбором; это отдельная задача со своей ценой, а частный ответ уже даёт трассировщик.
- **Редактирование баз** — `.dat` приходят из внешних источников и перезаписываются обновлением.
- **Виртуализацию списков** — обрезание до 300 строк и пагинация решают ту же проблему без
  новой зависимости.
