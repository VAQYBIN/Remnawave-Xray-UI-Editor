# Библиотека рецептов — дизайн

Направление 4 фазы 3. Опирается на уже готовые диагностику (трассировщик, geo, проверка ядром)
и безопасность правок (история, `writeDraft`, `DiffView`).

## Задача

Типовые конфигурации — WARP для отдельных сервисов, блокировка торрентов и рекламы, защита
локальной сети ноды, цепочка через второй сервер — сейчас собираются руками: узел за узлом,
правило за правилом. Рецепт делает это одной операцией, показывая заранее, что именно
изменится, и откатываясь одним Ctrl+Z.

Рецепт — не мастер и не отдельный режим. Это заготовка, которая **складывается** с уже
существующим конфигом: применили WARP, потом блок торрентов, потом цепочку — получили
работающую комбинацию, а не три несовместимых шаблона.

## Движок: план вместо мутации

Каждый рецепт — чистая функция в новом слое `entities/xray/recipes/`:

```ts
plan(config: XrayConfig, params: P): RecipePlan
```

```ts
export interface RecipeChange {
  status: 'add' | 'exists'   // «+» или «✓ уже есть»
  text: string               // «outbound warp», «правило geosite:openai → warp (первым)»
}

export interface RecipePlan {
  config: XrayConfig      // результат применения; исходный не мутируется
  changes: RecipeChange[] // строки предпросмотра, в порядке применения
  notes: string[]         // предупреждения рецепта («нужны geo-базы», «sniffing будет включён»)
}
```

Функция всегда возвращает полный план — и когда добавлять нечего. UI решает по наличию
хотя бы одного `add`, активна ли кнопка «Применить». Это же даёт бесплатный предпросмотр:
план строится на каждое изменение параметров, применение — просто `writeDraft` результата.

### Примитивы слияния (`recipes/apply.ts`)

Три функции, на которых собраны все рецепты. Каждая возвращает `{ config, status }`:

- `ensureOutbound(config, outbound)` — тег свободен: добавляем; тег занят: **берём существующий
  как есть**, настройки не трогаем (у пользователя мог быть настроен свой `block` или `warp`),
  статус `exists`.
- `ensureRule(config, rule, placement)` — ищет эквивалентное правило; нет — вставляет.
  `placement: 'block' | 'route'` (см. ниже).
- `ensureSniffing(config, inboundTags)` — ставит `sniffing.enabled = true`, и если
  `destOverride` пуст, заполняет его `['http', 'tls', 'quic']`. Возвращает статус по каждому
  затронутому inbound'у: правило по `protocol` без sniffing не сработает вовсе.

**Эквивалентность правил.** Сравниваются нормализованные значения: `domain`, `ip`,
`inboundTag`, `protocol`, `network` — как множества (порядок в них не значим), `outboundTag`,
`port`, `source`, `user` — точным равенством. Правило считается тем же, если совпали все
заданные поля обоих. Это ловит и повторное применение рецепта, и правило, набранное руками.

**Позиция правила.** В Xray выигрывает первое совпавшее правило, поэтому вставка в хвост под
общим «всё → proxy» не сработала бы никогда. Все рецептные правила идут **в начало**
`routing.rules`: `placement: 'block'` — в самое начало (индекс 0), `placement: 'route'` — сразу
за ведущей серией блокирующих правил, то есть за префиксом списка, у которого `outboundTag`
указывает на outbound с `protocol: 'blackhole'`. Так маршрут не перекрывает блокировку и не
уходит под пользовательские правила. Позиция отражается в тексте изменения («первым»,
«третьим»). Дальше правило двигается кнопками ↑/↓ в инспекторе — они уже есть.

### Реестр

`recipes/index.ts` экспортирует массив `RECIPES` с описанием каждого рецепта: `id`, `title`,
`summary`, `defaults` и `plan`. Параметры у рецептов разные, поэтому связка «рецепт → форма
параметров» — `switch` по `id` в UI; типобезопасность держится на дискриминированном
объединении `RecipeParams`, а не на дженериках в реестре.

## Пять рецептов

### 1. WARP для выбранных сервисов (`warp`)

Добавляет outbound `wireguard` (шаблон `WARP_TEMPLATE` из `OutboundForm` переезжает в
`recipes/warp.ts`, форма импортирует его оттуда) и **одно** правило с массивом категорий.

Параметры: тег (`warp` по умолчанию); чекбоксы категорий — OpenAI, Google, Netflix, Spotify,
Twitter/X, Meta, Discord, TikTok, Apple, Microsoft (коды `geosite:openai`, `geosite:google`,
`geosite:netflix`, `geosite:spotify`, `geosite:twitter`, `geosite:facebook`, `geosite:discord`,
`geosite:tiktok`, `geosite:apple`, `geosite:microsoft`); поле «свои домены и категории»
(`StringListField`); `secretKey`, `address` (v4 и v6), `reserved`, `mtu`.

Валидация: без хотя бы одной категории или своего домена правило бессмысленно — «Выберите
сервисы или укажите домены»; пустой `secretKey` — «Вставьте приватный ключ или нажмите
„Получить ключи“».

Замечание в `notes`: категории `geosite:` требуют загруженных geo-баз — иначе ядро откажется
стартовать. Проверяется по уже существующему запросу статуса geo; кнопка «Geo-базы» открывает
существующий диалог.

### 2. Блокировка торрентов (`torrent`)

`ensureOutbound({ tag: 'block', protocol: 'blackhole', settings: {} })`,
`ensureRule({ protocol: ['bittorrent'], outboundTag: 'block' }, 'block')`,
`ensureSniffing` по выбранным inbound'ам.

Параметры: тег блокирующего outbound'а (`block`), список inbound'ов (по умолчанию все).
Без sniffing правило не работает — поэтому включение sniffing не опция, а часть рецепта,
и оно показано отдельной строкой предпросмотра для каждого inbound'а.

### 3. Блокировка рекламы (`ads`)

`ensureOutbound(block)` + `ensureRule({ domain: ['geosite:category-ads-all'], outboundTag: 'block' }, 'block')`.
Параметр один — тег блокирующего outbound'а. Замечание про geo-базы, как у WARP.

### 4. Блокировка локальных сетей (`private`)

`ensureOutbound(block)` + `ensureRule({ ip: ['geoip:private'], outboundTag: 'block' }, 'block')`
+ `ensureRule({ domain: ['geosite:private'], outboundTag: 'block' }, 'block')`.

Закрывает клиентам доступ к локальной сети ноды и к самому серверу — типовая дыра в конфигах
Remnawave. Два правила, а не одно: `ip` и `domain` в одном правиле работают по «или», но
разделение читается яснее в топологии и по отдельности отключается.

### 5. Цепочка через другой сервер (`chain`)

Добавляет outbound на второй сервер и правило, направляющее в него выбранный трафик.

Параметры: тег (`chain` по умолчанию); протокол `vless | trojan | socks`; адрес и порт;
UUID (vless) либо пароль (trojan/socks) и, для socks, имя пользователя; чекбокс «TLS»
(`streamSettings.security = 'tls'`, `serverName` = адрес); для vless — `flow` пустой (цепочка
между серверами Vision не требует); селект «Подключаться через существующий outbound» →
`streamSettings.sockopt.dialerProxy` (второй хоп в одном соединении); домены и категории
(пусто = правило без условий, то есть весь трафик).

Валидация: адрес и порт обязательны; UUID проверяется формой (тот же regex, что в инспекторе);
`dialerProxy` не может указывать на собственный тег.

Отдельного рецепта «разблокировка через geo» нет: это WARP или цепочка с выбранными
категориями — тот же результат, но с явной точкой выхода.

## Ключи WARP: руками и кнопкой

Форма принимает `secretKey`, адреса и `reserved` вручную (пользователь берёт их из `wgcf` или
приложения WARP). Рядом — кнопка «Получить ключи», которая обращается к новой ручке.

### `POST /api/tools/warp-account`

Бэкенд, модуль `backend/src/tools/warp.ts`:

1. Генерирует пару X25519. Формат отличается от Reality: WARP принимает **обычный base64 с
   padding**, а `tools/reality.ts` отдаёт base64url без padding. Поэтому в `reality.ts`
   добавляется экспорт сырых байт (`generateX25519Raw(): { privateKey: Buffer; publicKey: Buffer }`),
   а обе кодировки живут в вызывающих модулях.
2. `POST https://api.cloudflareclient.com/v0a2158/reg` с телом
   `{ key, install_id: '', fcm_token: '', tos: <ISO-время>, model: 'PC', serial_number: '', locale: 'en_US' }`
   и заголовками `CF-Client-Version: a-6.10-2158`, `User-Agent: okhttp/3.12.1`.
3. `PATCH .../reg/<id>` с `{ warp_enabled: true }` и `Authorization: Bearer <token>` — без этого
   шага аккаунт создан, но WARP на нём не включён.
4. Ответ приводится к виду:
   `{ secretKey, address: ['172.16.0.2/32', '<v6>/128'], reserved: [n, n, n], peer: { publicKey, endpoint } }`.
   `reserved` — три байта `client_id`, декодированного из base64.

Исходящие запросы идут через `net/guard.ts`. Сейчас `fetchExternal` умеет только GET, поэтому
в него добавляется необязательный параметр `init` (`method`, `headers`, `body`) — проверка
хостов и ручные редиректы остаются прежними. Таймаут 10 с.

API неофициальный и может измениться. Любая ошибка — сетевая, нестатусный ответ, неожиданная
форма JSON — превращается в 502 с русским текстом «Cloudflare не выдал аккаунт WARP: <причина>.
Введите ключи вручную (wgcf)». Форма остаётся заполняемой руками: кнопка — удобство, а не
единственный путь. Ответ нигде не сохраняется — ключи попадают в конфиг профиля.

## UI

### Диалог рецептов

`features/recipes/RecipesDialog.tsx` — две колонки: слева список рецептов (название + короткое
описание), справа форма параметров выбранного, под ней предпросмотр изменений и замечания.
Внизу «Показать diff» и «Применить».

```
┌──────────────┬────────────────────────────────┐
│ WARP        ›│ WARP для выбранных сервисов    │
│ Торренты     │ Тег: [warp]                    │
│ Реклама      │ Сервисы: ☑ OpenAI ☑ Google …   │
│ Локальные сети│ Ключ: […] [Получить ключи]    │
│ Цепочка      │ ── Будет добавлено ──          │
│              │ + outbound warp                │
│              │ + правило geosite:openai → warp│
└──────────────┴────────────────────────────────┘
                    [Показать diff] [Применить]
```

«Показать diff» подменяет содержимое того же диалога на общий `DiffView` (текущий черновик
против результата) с кнопкой «Назад» — вложенный `<dialog>` не открывается, как и в «Версиях».

Вход — кнопка «+ Рецепт» в доке топологии, рядом с «+ Inbound / + Outbound / + Правило»:
смысл тот же, «добавить в схему», только целой заготовкой. Топбар не растёт, там уже шесть
кнопок.

Формы параметров — отдельные компоненты в `features/recipes/forms/` (`WarpForm`, `TorrentForm`,
`BlockForm`, `ChainForm`), на существующих примитивах `fields.tsx` / `collections.tsx`.
`BlockForm` обслуживает рецепты рекламы и локальных сетей — у них один параметр.

### Применение

`RecipesDialog` получает текущий конфиг и колбэк `onApply(config)`. `EditorPage` проводит его
через `changeConfig`, то есть через `writeDraft(text, { history: true })` — рецепт становится
одним снимком истории и откатывается одним Ctrl+Z. После применения диалог закрывается и
выбранный узел сбрасывается: правила вставляются в начало списка, поэтому позиционные
идентификаторы `rule:N` дрейфуют (урок плана 4 фазы 1).

### Второй вход: создание профиля

В `CreateProfileDialog` к выбору шаблона добавляются чекбоксы «Блокировать торренты»,
«Блокировать рекламу», «Блокировать локальные сети». Отмеченные рецепты прогоняются тем же
движком поверх `TEMPLATE` / `realityTemplate` перед отправкой в панель. WARP и цепочка туда не
попадают: им нужен ввод, для этого есть редактор.

## Ошибки и деградация

- Невалидные параметры — текст под полем, «Применить» заблокирована; план всё равно строится
  из того, что уже введено, чтобы предпросмотр не мигал пустотой.
- Пустой план (всё уже есть) — «Применить» заблокирована, строки показывают `✓` у каждой части.
- Geo-базы не загружены — замечание в `notes` и кнопка «Geo-базы»; рецепт при этом применяется:
  конфиг корректен, не хватает только данных на ноде.
- `POST /api/tools/warp-account` упал — сообщение под кнопкой, поля остаются доступны для
  ручного ввода.
- Конфиг не парсится — кнопка «+ Рецепт» недоступна, как и остальные кнопки дока: рецепт
  работает с разобранным `XrayConfig`.

## Тестирование

**Unit (`entities/xray/recipes`)**: примитивы слияния — занятый тег переиспользуется без правки
настроек; эквивалентное правило не дублируется (в том числе при другом порядке значений внутри
`domain`); `ensureSniffing` не трогает уже включённый sniffing и заполняет пустой `destOverride`.
По каждому рецепту: план на пустом конфиге, повторный прогон даёт только `exists`, позиция
блокирующего правила выше маршрутного, валидация параметров.

**Backend**: `warp.ts` на стабе `fetch` — успешная регистрация (проверяется тело запроса,
заголовки, вызов PATCH), `reserved` из `client_id`, отказ API → 502 с русским текстом, таймаут;
`fetchExternal` с `init` не теряет проверку хостов и редиректов.

**Компонентные**: `RecipesDialog` — переключение рецептов сохраняет введённые параметры,
«Применить» заблокирована при пустом плане и при ошибке валидации, «Показать diff» рисует обе
стороны, применение отдаёт конфиг с ожидаемыми правилами. `CreateProfileDialog` — отмеченные
чекбоксы попадают в отправляемый конфиг.

**E2E**: применение «Блокировки торрентов» из дока — на графе появляются узел `block` и правило,
Ctrl+Z откатывает, повторное открытие рецепта показывает `✓ уже есть`.

## Что осознанно не делаем

- Не сохраняем параметры рецептов между сессиями: ключи и адреса оседают в конфиге, остальное
  вводится за секунды.
- Не редактируем и не удаляем «применённый рецепт» как единое целое: после применения это
  обычные узлы и правила, и правятся они обычными формами. Отслеживание принадлежности узлов
  рецепту потребовало бы метаданных в конфиге, который уходит в панель.
- Не даём пользователю сочинять свои рецепты: библиотека закрытая, пять штук.
