# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Визуальный редактор Xray-конфигов панели Remnawave 2.8+/3.x: топология трафика как граф (React Flow), формы вместо ручного JSON, сохранение в панель по API. Редактор работает с двумя сущностями панели: конфиг-профилями нод и шаблонами подписок (тип `XRAY_JSON`) — общая оболочка `Workbench`/`useConfigDraft`, но своя логика сохранения и оптимистической блокировки у каждой (см. «Особенности домена»). Язык UI, сообщений об ошибках и документации — русский; коммиты — английский conventional style (`fix(frontend): ...`). Ветки: `main` и рабочая `dev`.

## Команды

npm workspaces: `backend` + `frontend`. Из корня:

```bash
npm run dev            # dev-сервер бэкенда (tsx watch, нужен .env — см. .env.example)
npm run dev:frontend   # Vite на :5173, проксирует /api на :3000
npm test               # тесты обоих workspace
npm run build          # tsup (backend) + tsc --noEmit && vite build (frontend)

npm test -w backend                       # vitest бэкенда
npm test -w frontend                      # vitest фронтенда
npm run typecheck -w backend              # tsc --noEmit (аналогично -w frontend)
npx vitest run test/auth.test.ts          # один тест-файл (из каталога workspace)
npm run e2e -w frontend                   # Playwright e2e (перед первым запуском И после
                                          # обновления playwright — у каждой версии свой билд:
                                          #   cd frontend && npx playwright install chromium)
```

Три тестовых контура фронтенда не пересекаются:
- **vitest** берёт только `test/**/*.test.{ts,tsx}` (jsdom);
- **Playwright** (`e2e/*.spec.ts`) поднимает собственный dev-сервер на `127.0.0.1:4173` и мокает API через `e2e/mocks.ts` — бэкенд не нужен;
- `tsc --noEmit` не проверяет каталог `e2e` (не входит в `include` tsconfig).

Четвёртый контур — **скриншоты** для README: `npm run screenshots -w frontend`
(`screenshots/*.spec.ts`, свой `playwright.screenshots.config.ts` и порт 4175). Ничего не
проверяет, пишет PNG в `docs/screenshots/` на витринном конфиге `screenshots/showcase.ts`;
в `npm test` и `npm run e2e` не входит. Анимации там **не глушатся**: `RemeasureOnEnter`
пересчитывает якоря рёбер по `animationend`, и без него рёбра уедут на 8px ниже гнёзд.

## Архитектура

### Backend (`backend/src`) — Fastify, ESM, Node 24

Тонкий защищённый прокси к API панели Remnawave. Токен панели живёт только на сервере; браузер ходит на `/api/*` с сессионной cookie.

- `server.ts` — `buildServer(config, deps)`: сборка приложения. Через `deps` инжектятся `RemnawavePort` и `BackupService` — так тесты подменяют панель стабом (`test/stub-remnawave.ts`).
- `remnawave/client.ts` — `RemnawaveClient` (реализация `RemnawavePort`), все ошибки панели заворачиваются в `RemnawaveError` и превращаются глобальным error handler'ом в JSON-ответы с исходным статусом.
- `routes/profiles.ts` — ключевой флоу сохранения: `PATCH /api/profiles/:uuid` требует `expectedUpdatedAt`; при расхождении — `409` с актуальным профилем (оптимистическая блокировка). Перед каждым обновлением текущая версия пишется в бэкап (`backups/service.ts`, каталог `DATA_DIR/backups/<uuid>/`).
- `routes/templates.ts` — пять роутов (список, чтение, создание, удаление, `PATCH`) для шаблонов
  подписки. У шаблона нет `updatedAt`, поэтому `PATCH` сравнивает не версию, а **хэш содержимого**
  (`expectedHash` в теле): расхождение — тот же `409`, что у профилей. Хэш считает и сравнивает
  только бэкенд (`templates/hash.ts`), и способов у него два по виду содержимого: у JSON-шаблона
  хэшируется канонизованный `templateJson` (`canonicalize` — рекурсивная сортировка ключей
  объектов через `Object.create(null)`, иначе `__proto__` из чужого JSON молча выпал бы из хэша;
  порядок элементов массивов сохраняется — в списке правил маршрутизации он значим), у YAML-шаблона
  (`YAML_TEMPLATE_TYPES`) — сам ТЕКСТ `encodedTemplateYaml` без всякой нормализации: любая сделала
  бы хэш слепым к правке, которую панель сохранит. Создание у панели двухшаговое (`POST` заводит
  пустой шаблон, содержимое льётся отдельным `PATCH`); ручка склеивает оба вызова и подставляет
  каркас по типу — `templates/starter.ts` для `XRAY_JSON` (локальные inbound'ы, одна группа
  подстановки, минимум outbound'ов), `templates/starterMihomo.ts` для `MIHOMO` либо
  `templates/starterSingbox.ts` для `SINGBOX`. Пустой шаблон
  панель тоже создаёт, но подписка из него не отдаст клиенту ни одного сервера. Редактор умеет
  **три** типа — `XRAY_JSON`, `MIHOMO` и `SINGBOX` (единственный источник списка —
  `EDITABLE_TEMPLATE_TYPES` в `routes/templates.ts`, его же читает схема создания); на
  остальных (`CLASH`, `STASH`, `XRAY_BASE64`)
  `PATCH` отвечает `400`, и это белый список, а не чёрный: новый тип панели обязан молча получить
  `400`, а не молча пройти. Проверка типа стоит ПЕРЕД проверкой поля содержимого — иначе на
  `XRAY_BASE64` сработала бы более ранняя «нужен templateJson», а дело не в поле.
  Бэкапы шаблонов лежат в отдельном пространстве
  `DATA_DIR/backups/templates/<uuid>/` (роуты чтения — в `routes/backups.ts`), а не рядом с
  бэкапами профилей: uuid профиля и шаблона могут совпасть, общий путь вернул бы чужие версии.
  `routes/nameSchema.ts` — общая для имени профиля и шаблона регулярка (`/^[A-Za-z0-9_\s-]+$/`,
  латиница/цифры/пробел/`-`/`_`), зеркалит проверку панели: расширять нельзя, панель всё равно
  откажет, только позже и по-английски. `backend/test/contract.test-types.ts` — тест на уровне
  типов (падает на `tsc --noEmit`, ничего не выполняет) против `@remnawave/backend-contract`
  (только devDependency, только `import type`) — ловит расхождение наших интерфейсов с контрактом
  панели, не блокируя проход неизвестных полей в рантайме.
- `auth/*` — вход по паролю, подписанная httpOnly-cookie, guard закрывает все `/api/*` кроме
  auth/health. В `.env` `APP_PASSWORD` может быть и открытым текстом, и bcrypt-хэшем, но
  `loadConfig` хэширует открытый на старте — в `AppConfig.appPassword` всегда лежит хэш, и
  `verifyPassword` знает единственный формат. Rate-limit двухуровневый: 5 попыток в минуту на
  логине и глобальные 600 запросов в минуту на остальное.
- `xray/*` — проверка конфига ядром: `panelClients.ts` берёт по одному настоящему клиенту из
  `computed-config` профиля, `dummyClient.ts` подставляет фиктивного там, где пары не нашлось
  (профили панели хранятся с `clients: []`), `service.ts` запускает `xray run -test` с
  `XRAY_LOCATION_ASSET` на geo-базы из `DATA_DIR`, `parseOutput.ts` переводит цепочки ошибок ядра
  в русские подсказки. Нет бинаря (`XRAY_BIN`) — `available: false`, а не ошибка.
- `mihomo/*` — та же идея для шаблонов Mihomo: `dummyProxies.ts` подставляет фиктивные `proxies` в
  корень и в группы/inline-провайдеров с маркером или без кандидатов (панель хранит их пустыми —
  ядро такой документ не примет), `service.ts` (`MihomoService`, ручка `POST
  /api/tools/mihomo-test`) пишет результат во временный файл и запускает `mihomo -t -f`, снимая файл
  сразу после. Общий с `xray/service.ts` запуск процесса вынесен в `proc/spawn.ts`
  (`runProcess`/`SpawnRunner`) — раньше это было бы второй копией той же обвязки над
  `child_process`. Бинарь берётся из `MIHOMO_BIN`; нет бинаря — `available: false`, как у Xray.
  `withDummyProxies` зовёт `parse()` ДО входа в try сервиса: `YAMLParseError` на невалидном
  документе ловится в самом роуте и превращается в `400` с русским текстом — иначе кнопку
  «проверить ядром» жмут именно тогда, когда с документом что-то не так, и получали бы `500`
  движка на английском.
- `singbox/*` — то же самое третий раз, для шаблонов Sing-box: `dummyOutbounds.ts` дописывает
  фиктивные серверы В КОНЕЦ `outbounds` и перезаписывает списки групп (`selector` получает
  прокси и теги `urltest`-групп, `urltest` — только прокси), пропуская группы с
  `remnawave.includeProxies: false`, и вырезает сам ключ `remnawave`. Это не наша выдумка про
  «как правильно», а повторение генератора панели: разойдись мы с ним — и вердикт ядра был бы
  ответом про другой документ. Порядок значим отдельно: при пустом `route.final` ядро берёт
  ПЕРВЫЙ элемент `outbounds`, поэтому дописывание в конец меняет смысл документа, а
  дописывание в начало сломало бы его. `service.ts` (`SingboxService`, ручка `POST
  /api/tools/singbox-test`) запускает `sing-box check -c` по временному файлу; бинарь — из
  `SINGBOX_BIN`, нет бинаря — `available: false`. В образе лежит musl-сборка ядра, а не
  «обычная»: glibc-архив в alpine не запускается вовсе.
- `tools/realityProbe.ts` — TLS-проба Reality-цели (TLS 1.3, ALPN h2, X25519, покрытие
  `serverNames` сертификатом, проверка цепочки, подозрение на CDN). Исходящие соединения обоих
  инструментов проходят через `net/guard.ts` (`assertPublicHost`/`fetchExternal`) — приватные,
  loopback, link-local и CGNAT-адреса отклоняются, у geo есть опт-ин `GEO_ALLOW_PRIVATE_URLS`.
- `tools/warp.ts` — регистрация бесплатного аккаунта Cloudflare WARP (то же, что делает `wgcf`):
  POST `/reg` + PATCH `warp_enabled`, ответ приводится к настройкам wireguard-outbound. Оба
  запроса идут через `fetchExternal` с параметром `init` (метод/заголовки/тело) — обходить guard
  нельзя. API неофициальный, поэтому ручка отвечает 502 с русским текстом, а не 500: в форме
  рецепта остаётся ручной ввод ключей. Ключ здесь в обычном base64 с padding, у Reality —
  base64url без padding; общая генерация сырых байт — `generateX25519Raw` в `tools/reality.ts`.
- `geo/*` — разбор `geosite.dat`/`geoip.dat` (свой декодер protobuf), настраиваемые источники в
  `DATA_DIR/settings.json`, ответы на вопрос «входит ли домен/IP в категорию». Коды категорий в
  `.dat` лежат в ВЕРХНЕМ регистре — поиск по исходной строке из конфига всегда промахнётся.
  Просмотр баз: `categories(kind)` считает размеры категорий через `countEntries` (проход по
  байтам без разбора — полный разбор всей базы стоил бы сотни мегабайт), `categoryPage` режет
  содержимое по `offset`/`limit` и фильтрует по `q`, пересчитывая `total`. Кэш разобранных
  категорий ограничен восемью на вид (`MAX_PARSED`): вьюер листает категории подряд, а `US` в
  geoip — 336 502 подсети. UI — `features/diagnostics/GeoBrowser.tsx` во вкладке диалога
  «Geo-базы»; кнопка «В правило» идёт через `appendGeoKey` в `entities/graph/mutations.ts`.
- `config.ts` — env валидируется zod'ом при старте; отдельная проверка ловит bcrypt-хэш, испорченный интерполяцией `$` в Docker Compose (см. README).
- Статика фронтенда отдаётся из `STATIC_DIR` с SPA-fallback на `index.html`; неизвестные `/api/*` — JSON 404.
- `catalog/service.ts` — каталог готовых шаблонов из `remnawave/templates`. Ссылку на содержимое
  принимаем только ту, что пришла в индексе: произвольный `url` от клиента — дыра в SSRF-защите,
  которую `net/guard.ts` уже закрывает по хостам, но не по назначению.

### Frontend (`frontend/src`) — React 19, Vite, слоистая структура

`shared` → `entities` → `features` (вариация feature-sliced):

- `entities/xray` — типы и чистая логика Xray-конфига: схемы inbound/outbound/stream/routing, генерация (`generate.ts`). Всё реэкспортируется через `entities/xray/index.ts`.
  Транспорт узла читается **только** через `streamNetwork` (`compat.ts`): Xray v26.7.28
  переименовал `streamSettings.network` в `method` и при обоих ключах слушает `method`, поэтому
  форма при смене транспорта пишет `network` и удаляет `method`.
- `entities/graph` — `buildGraph.ts` строит из конфига колоночный граф (squad → inbound → rule → outbound); `mutations.ts` — обратные правки конфига из графа. Дубликаты тегов пропускаются (иначе ломаются id узлов React Flow).
- **Балансеры.** `routing.balancers` — своя колонка графа между правилами и outbound'ами
  (`COLUMN_X.balancer`, outbound уехал на 1290), узел `bal:<tag>`. `selector` матчит теги
  outbound'ов **по префиксу**; единственная реализация — `entities/xray/balancers.ts`
  (`matchPrefixes`/`balancerCandidates`), её зовут граф, форма, валидации, трассировка и рецепт.
  Разрыв ребра «балансер → выход», заданного префиксом, `disconnectEdge` не выполняет (возвращает
  тот же конфиг) — `TopologyView` спрашивает подтверждение и вызывает `expandSelector`. У ребра
  запасного выхода свой префикс id (`e:bal:<tag>->fb:<out>`): тег может быть и кандидатом, и
  fallback'ом, а одинаковые id ломают React Flow. `observatory`/`burstObservatory` — глобальные
  секции (по одной на конфиг), живут в узле `obs` под колонкой балансеров; `leastPing` требует
  первую, `leastLoad` — вторую, заводит их кнопка в форме балансера через
  `ensureObservatorySection`. При заданных сразу `outboundTag` и `balancerTag` ядро берёт
  `outboundTag`, поэтому мутации графа снимают парный тег.
- **Шаблоны подписки.** `entities/xray/inject.ts` разбирает директиву `remnawave.injectHosts`:
  панель на её основе строит outbound'ы, которых в документе физически нет, и вставляет их **в
  начало массива** `outbounds` — правила и балансеры ссылаются на них по тегу. Тег
  предсказуем (`predictedTags`/`tagScheme`) только при `tagPrefix` (`proxy`, `proxy-2`, …); при
  `useHostRemarkAsTag`/`useHostTagAsTag` тег знает только панель — `predictedTags` тогда
  возвращает пусто, а `hasPanelNamedTags` подавляет по всему документу проверки «неизвестный
  outbound-тег» и «у балансера нет кандидатов» (иначе корректный шаблон дал бы ложную тревогу).
  Отсюда же дефолтный маршрут трассировки: если ни одно правило не совпало, трафик уходит не в
  `outbounds[0]`, а в первый подставленный сервер первой группы — `entities/xray/trace.ts` называет
  именно её, потому что порядок вставки МЕЖДУ группами панель не документирует (осознанное
  предположение, не факт). Граф рисует группу узлом `inj:<index>` в колонке outbound'ов
  (`COLUMN_X.outbound`) перед статическими выходами. `entities/graph/edgeIds.ts` — единственная
  схема id рёбер (`edgeId`, `fallbackEdgeId`, `outboundTargets`): ребро к инжектируемому тегу ведёт
  в `inj:<index>`, а не в `out:<tag>` — статического узла для такого тега нет. Разрыв ребра
  «балансер → выход», если тег ловится префиксом группы подстановки, неразрешим тем же способом,
  что и обычный префикс-разрыв: `blockingInjectPrefix`/`blockingGroupPrefix`
  (`entities/xray/balancers.ts`, `entities/graph/mutations.ts`) объясняют это в подтверждении, а
  `expandSelector` такие префиксы **не разворачивает** — сохранит группу и вернётся к разрыву,
  развернёт и сломает предсказание тегов; при тегах от панели разворот запрещён целиком. Гнездо
  узла группы при схеме, отличной от `tagPrefix`, закрыто (`isConnectable`): предсказанного тега
  нет, мутация вернула бы тот же конфиг и кабель тянулся бы вхолостую. Завести группу с холста
  можно кнопкой «+ Подстановка» — она появляется только у `TemplateEditorPage` (проп
  `allowInject` через `Workbench`), в редакторе профиля секции `remnawave` нет. Префикс новой
  группы нумеруется БЕЗ дефиса (`proxy`, `proxy2`, `proxy3`): дефисом панель называет второй и
  следующие хосты ВНУТРИ группы, поэтому `proxy-2` столкнулся бы с предсказанным тегом соседней
  группы. Занятыми считаются `outboundTagsOf` — статические теги и все предсказанные. UI — `features/templates/*` (`TemplatesPage`,
  `TemplateEditorPage`, `CreateTemplateDialog`) и `features/inspector/InjectGroupForm.tsx` (способ
  именования — ровно один из трёх ключей, форма делает состояние «два сразу» невыразимым, как и
  сама `withTagScheme`). Список шаблонов показывает все типы панели, но открыть на редактирование
  можно `XRAY_JSON`, `MIHOMO` и `SINGBOX` — остальные (`CLASH`, `STASH`, `XRAY_BASE64`)
  ведут в панель. Переключатель разделов — `features/nav/SectionSwitch.tsx`.
- **Общий слой схемы и форм.** `shared/schema` — типы и чистые функции над деревом `FieldSchema`
  без знания о конкретном ядре (`types.ts`, `resolve.ts`, `ops.ts`): условие видимости `when`
  сравнивает соседа СТРОКОЙ и умеет `in` и, для случаев вроде dial-полей выхода (нужны всем типам,
  кроме групп), `notIn` — список исключений не устаревает на каждом новом типе ядра, в отличие от
  списка «всех остальных»; вид поля `map` — отображение строка → строка (заголовки транспорта,
  `hosts`), без него такой ключ был бы объектом без полей и рисовался бы только на чтение;
  `fieldsAt`/`fieldAt`/`visibleFields`/`unknownKeys`/`deprecatedAt`/`walkSchema` — спуск по пути с
  учётом `when` и текущего значения. Писатель — операции `DocOp` (`set`/`remove`/`insert`/`move`)
  и `applyOps`, который правит КОПИЮ модели (`structuredClone`: вход держит React, правка на месте
  не вызвала бы перерисовку), плюс интерфейс `DocWriter` (`apply`/`lockAt`) — форма никогда не
  отдаёт наружу целое значение, только эмитит операции по АБСОЛЮТНОМУ пути.
  `features/inspector/schema/SchemaForm.tsx` — один рендерер на общем формате: заполненные поля
  наверху, незаполненные
  — под `CollapsibleSection` «Ещё поля (N)», и одно только выполнившееся условие `when` туда
  наверх НЕ поднимает (в реальном словаре условным оказывается почти каждое поле — иначе крышка
  опустела бы, а верх формы захламили бы десятки полей, ставших доступными, но не заполненных).
  Ключ вне схемы виден всегда и только на чтение; значение не той формы, что ждёт словарь (строка
  вместо объекта), — тоже на чтение; замок писателя (`writer.lockAt(path)`) — на чтение с его
  причиной. Список строк со ссылкой (`item.ref`) рисуется мультиселектом по тегам документа с тем
  же сквозным пропуском чужого значения, что у одиночного `ref`. `shared/ui/MenuButton` — кнопка-
  меню на том же портальном списке, что `Select`. `TriStateField` (`features/inspector/fields.tsx`)
  — трёхпозиционный контрол «не задано / да / нет»: явное `false` обязано быть выразимо и
  отличимо от отсутствия ключа. `NumberField` того же файла ресинхронизирует текстовый буфер,
  когда `value` меняется НЕ из-за собственного `onChange` (смена узла, отмена/возврат) — без этого
  поле продолжало бы показывать число прежнего владельца позиции. Формы Xray эту схему не
  используют — её тесты контрольная группа, и правка общего слоя обязана оставлять их нетронутыми;
  sing-box и Mihomo читают её оба, и расширения под них аддитивны: `Lock.action?: { label; run }`
  — необязательное действие у замка (`SchemaForm` рисует под запертым полем кнопку с этой
  подписью; нужно материализации якоря у Mihomo, см. «Отказ вместо порчи» ниже — у sing-box замков
  с действием нет); `FieldSchema.values` у `kind: 'map'` — `'string' | 'strings'` (по умолчанию
  `'string'`, то же правило «скаляр как список из одного элемента», что у `ref`-полей, но для
  отображения строка → строка — `dns.nameserver-policy`, `hosts` у Mihomo); `ListItemSchema.kind:
  'port'` — элемент «число либо строка-диапазон» (`[80, 8080-8880]`), строка целиком из цифр
  пишется числом; `RefKind` получил `'proxy-target' | 'provider' | 'sub-rule'`. Панель «Документ»
  обобщена в `features/inspector/schema/DocPanel.tsx` (разделы, писатель, ссылки, `fieldsAt`/
  `fieldAt` и таблицы форм для списков и отображений приходят пропсами) — `SingboxDocPanel` и
  `MihomoDocPanel` — тонкие обёртки над ней; тесты `SingboxDocPanel` не правились при вынесении, и
  сам факт, что они прошли без изменений, — проверка, что извлечение ничего не поменяло.

  `proxy-providers.<имя>`) так же, как в элемент списка по индексу.

- **Граф sing-box** (`entities/graph/singbox/buildGraph.ts`) — входы → правила → группы → выходы.
  Полос четыре, а колонок больше: полоса групп разворачивается по глубине ссылок тем же расчётом,
  что у Mihomo (`selector` перечисляет `urltest`, а закреплённая группа ссылается на что угодно),
  и кольцо ссылок глубину не вешает — ошибка приходит диагностикой из `validate.ts`. Узлы:
  `inbound:<tag>`, `rule:<index>`, `group:<tag>`, `out:<tag>`, `builtin:<action>`, `hosts:panel`;
  дедупликация id одна на все виды — React Flow на дубликате не падает, а тихо теряет узел с
  холста. Ребро «вход → правило» рисуется ТОЛЬКО когда правило само назвало вход полем `inbound`:
  у sing-box вход к маршруту не привязан, и связь «просто так» изобразила бы поток, которого нет.
  `hosts:panel` заводится, только когда панели есть куда класть серверы (жива хоть одна группа без
  `includeProxies: false`), — иначе это узел про подстановку, которой не будет. `builtin:<action>`
  — три ТЕРМИНАЛЬНЫХ действия (`reject`, `hijack-dns`, `bypass`), но узел из них достаётся не
  всем одинаково: `reject` и `hijack-dns` выход не называют никогда, а у `bypass` поле `outbound`
  необязательное (`configuration/route/rule_action`) — без него подбор завершает обход ядром
  (узел `builtin:bypass`), а с ним `bypass` ведёт туда же, куда и `route`: ребром к названному
  выходу, а не в builtin. Без узла на первом из этих исходов `bypass` нарисовался бы как `sniff` —
  правилом, которое никуда не ведёт, — а он ведёт, просто не всегда в outbound. DNS в граф не идёт
  вовсе: это независимый от маршрута механизм, и на одном холсте получились бы два разных графа
  поверх друг друга.
- **`endpoints` рисуются тем же узлом `out:<tag>`, что и `outbounds`**: для маршрута wireguard —
  такая же адресуемая тегом цель, а спрятать её с холста значило бы соврать, что маршрут ведёт в

  карточку, которую пользователь видит на холсте.

- **Сохранение шаблона sing-box блокирует ЛЮБАЯ ошибка**, а не только синтаксис, — и это
  осознанное расхождение с Mihomo. Там почти все диагностики про имена, которых редактор знать не
  может, и прятать за ними кнопку значило бы запретить сохранять корректный шаблон; здесь ошибки

  сломанную подписку. Тот же довод разводит уровни в `validate.ts`: незнакомый тег — всего лишь
  предупреждение, пока панели есть куда подставлять серверы; если подставлять некуда, это

  переписан руками) — про такой тип уже сказало предупреждение `deprecated` со своей причиной и
  заменой, и вторая, более общая претензия на том же пути документа была бы шумом. Ссылки на
  DNS-серверы и наборы правил (`dns.final`, `dns.rules[].server`, `route`/`dns`-правила с
  `action: resolve`, `default_domain_resolver`, `outbounds[].domain_resolver`) объявляет сам
  документ — панель сюда ничего не подставляет, поэтому неизвестный тег здесь ошибка безусловно,
  не «предупреждение, пока панель может дозаполнить», как у ссылок на outbound.

  нет разобранной модели документа, только дерево CodeMirror. Поэтому `context.ts` строит вдоль

- **Граф Mihomo** (`entities/graph/mihomo/buildGraph.ts`) — правила → группы → выходы, но колонка

  а маркер `# LEAVE THIS LINE!` она не читает вовсе (см. ниже) — прежнее условие по

  provider`, и ребро от правила либо группы на статический сервер рисуется тем же способом, что на
  группу. Дедупликация id одна на все виды: React Flow на дубликате не падает, а тихо теряет узел с
  холста. Из узла подстановки кабель не выходит — имена подставленных хостов известны только
  панели. `connectMihomo`/`disconnectMihomo` (`entities/graph/mihomo/mutations.ts`) возвращают
  операции писателя (`{ ops: DocOp[]; refusal?: MihomoRefusal }`) вместо текстовых правок — разрыв
  нескольких рёбер разом теперь одна пачка операций и один снимок истории, прежнее ограничение
  «за раз разрывается одна связь» снято; отказы остаются поимённо (`refusalText`).

  описываются отдельным списком в `context.ts`: это обычные поля родительской схемы со своим
  `doc`, и подсказка при наборе, и наведение читают один и тот же текст — второй список отставал
  бы от схемы на первом же новом контейнере.
- **Сохранение шаблона Mihomo** шлёт `encodedTemplateYaml` (base64 через `TextEncoder`, не `btoa`:
  в именах групп живых шаблонов есть кириллица и эмодзи) и тот же `expectedHash`, что у
  Xray-шаблона. Кнопка сохранения блокируется только на синтаксической ошибке YAML: остальные
  диагностики — предупреждения об именах, которых редактор знать не может, и прятать за ними
  кнопку значило бы запретить сохранять корректный шаблон.
- **Трассировка Mihomo останавливается** на правиле, чьё УСЛОВИЕ проверить нечем, и прямо
  называет причину (`entities/mihomo/trace.ts`, панель — `features/diagnostics/MihomoTracePanel.tsx`).
  Молчаливый пропуск дал бы уверенный неверный ответ: всё, что стоит ниже, выполняется ровно при
  условии, что непроверяемое правило не совпало, — а этого условия мы не знаем. Отсюда же и то,
  что правила НИЖЕ остановки в разбор не попадают. Останавливают: `RULE-SET`, по которому ответа
  нет, — ответ ещё едет либо набор недоступен (см. ниже); типы, читающие источник или вход, —
  `SRC-*`, `IN-*`, `UID`, `DSCP`, `IP-ASN`, `IP-SUFFIX` (`NO_DATA_TYPES` выводится из `RULE_TYPES`,
  а не переписывается руками — новый тип ядра попадёт туда сам); `PROCESS-*`, когда поле «процесс»
  в цели пусто, а `PROCESS-PATH*` — ещё и когда там указано только имя без разделителя пути;
  `GEOSITE`/`GEOIP`, когда базы не
  загружены или ответа по ключу нет; `IP-CIDR`/`IP-CIDR6` без IP в цели либо с неразбираемой
  подсетью; `DST-PORT` с неразбираемым списком портов; битый шаблон `DOMAIN-WILDCARD`/`DOMAIN-REGEX`;
  незнакомый тип; условие без значения; модификатор `src` (разворачивает правило на источник);
  неразбираемая строка правила.
  **Наборы правил редактор теперь спрашивает у бэкенда** (`POST /api/tools/ruleset/match`, хук
  `useRuleSetMatch` рядом с `useGeoMatch`, связывание — в `useMihomoDraft`). Дескрипторы собирает
  фронтенд (`entities/mihomo/ruleSets.ts`, четыре вида), но на сервер уходят только `http` и
  `inline`: набор из файла клиента (`file`) и набор незнакомого вида (`unsupported`) сервер не
  увидит по определению, и их состояние подмешивается как `unavailable` со своей причиной прямо в
  черновике — сеть для них не нужна. `domain` и `ipcidr` считает бэкенд (декодеры `.mrs` есть
  только там), а `classical` приезжает СТРОКАМИ и считается на фронтенде теми же правилами, что и
  правила документа: это правила Mihomo, и их вычислитель — здесь. Пока ответы в пути,
  `pending` даёт остановку с причиной «ещё загружается», а не промах. Отдельно: набор
  `behavior: ipcidr` БЕЗ `no-resolve` при цели без IP назначения отвечает не «нет», а отказом —
  ядро в этом случае домен резолвит и проверяет полученный адрес, которого редактор знать не
  может. На эталонном шаблоне (`test/fixtures/mihomo/roscomvpn.yaml`, приёмка —
  `test/mihomo-trace-acceptance.test.ts`) это ровно та причина, по которой цель без IP честно
  встаёт на правиле #30, а до `MATCH` доходит только полностью заданная цель.
  Поле «процесс» в цели трассировки покрывает все шесть типов `PROCESS-*`: `PROCESS-NAME`,
  `PROCESS-PATH` и их `-WILDCARD`/`-REGEX`-варианты. Шаблон `-REGEX` НЕ заякорен — ядро зовёт
  `MatchString`, а это поиск вхождения, поэтому `PROCESS-NAME-REGEX,discord` ловит и `discord.exe`,
  и `vesktop-discord.exe`.
  Если у сработавшего набора задано поле `proxy`, разбор дописывает оговорку: клиент качает такой
  набор через указанную группу, а редактор спрашивал его напрямую — содержимое могло отличаться.
  **Модификатор `no-resolve` снимает остановку** там, где правило смотрит только на IP назначения,
  а IP в цели не задан: ядро домен в этом случае не резолвит по прямому указанию документа,
  `DstIP` остаётся невалидным, и `Match` возвращает false — это ОПРЕДЕЛЁННЫЙ промах, а не
  неизвестность (`rules/common/ipcidr.go`, `geoip.go`; у `RULE-SET` при `noResolveIP` ядро зануляет
  сам колбэк резолва — `rules/provider/rule_set.go`). Список таких типов (`IP_ONLY_TYPES`) закрыт и
  короток намеренно: `IP-CIDR`, `IP-CIDR6`, `GEOIP` плюс `RULE-SET` ровно при `behavior: ipcidr` —
  туда попадает только то, чей `Match` прочитан в исходниках ядра. При `behavior: domain`
  и `classical`, у провайдера, которого в документе нет, и у `IP-SUFFIX`/`IP-ASN` остановка
  сохраняется. Без `no-resolve` она сохраняется тоже: там ядро как раз резолвит, и какой выйдет
  IP, редактор не знает.
  `AND`/`OR`/`NOT` пробрасывают неизвестность наверх, но её
  перевешивает точный ответ, решающий исход, — и он у каждого свой: у `AND` это «нет»
  (`AND(нет, неизвестно)` — «нет» при любом ответе), у `OR` — «да» (а вот «нет» неизвестность у
  `OR` НЕ перевешивает); у `NOT` перевешивать нечем, неизвестность единственного условия проходит
  насквозь.
  **`SUB-RULE` НЕ в этом списке**: он, наоборот, СПУСКАЕТСЯ в подсписок и разбирает его теми же
  правилами. Останавливает он только частными случаями: у правила нет условия, условие не
  разбирается, подсписка нет либо его значение не список, подсписок зациклился, либо неизвестность
  пришла из самого подсписка. (В таблице брифа задачи 15 `SUB-RULE` стоял среди останавливающих —
  это был дефект плана, отменённый ревью; в коде спуск.) Ни одно правило подсписка не подошло —
  проход возвращается в основной список: это ВЫВОД из документации ядра (`PASS` выводит из
  подсписка, ссылка на несуществующий подсписок откатывается туда же), а не прямое её утверждение.
  **В подсписок спускается и валидация** (`validateMihomo`) — теми же проверками, что и в
  основном списке: это правила Mihomo, а не другой язык, и молчать о них значило бы читаться
  как «всё в порядке». Путь диагностики — `sub-rules.<имя>.<индекс>`; резолвер графа ведёт по
  нему на карточку подсписка, отдельных узлов у его правил нет. Один вывод в подсписок НЕ
  переносится — «в конце нет MATCH»: там он был бы требованием ошибки, потому что «ничего не
  совпало» выводит обратно в основной список, а не в прямое соединение. Разбор строк-правил
  любого списка — один на всех (`ruleEntriesOf` в `rules.ts`): до этого он был переписан
  трижды, в `rules.ts`, `edits.ts` и `trace.ts`.
  Состояние наборов и их содержимое — три отдельные ручки: `POST
  /api/tools/ruleset/status` (по кэшу, СЕТЬ НЕ ТРОГАЕТ — иначе открытие диалога
  на живом шаблоне превращалось бы в 26 загрузок), `refresh` (принудительная
  перезагрузка одной ссылки или всех) и `page` (постраничное содержимое с
  поиском). У наборных роутов свой `bodyLimit` в 8 МБ: числом наборов запрос НЕ
  ограничен намеренно — предел на документ живёт в сервисе и отвечает причиной
  по каждому лишнему набору, а отказ схемой обнулял бы ответы по всему
  документу. Просмотрщик показывает у набора доменов ВДВОЕ больше строк, чем
  записей в заголовке: на каждый домен ядро кладёт и сам домен, и форму
  `+.<домен>` — оба числа показываются рядом. Недоступный набор становится
  предупреждением в общем списке диагностик (`useMihomoDraft` склеивает их с
  диагностиками документа: состояние набора выводится из `md`, а `md` приходит
  из `useDocumentDraft`, и передать их внутрь значило бы замкнуть круг); у пути
  `rule-providers` появился переход — на псевдоузел `doc:settings` (панель «Документ»):
  раньше узла для него не было вовсе, и такая диагностика была не кликабельна.
  Строки набора `classical` идут и в вопрос к geo-базе: `GEOSITE`/`GEOIP` внутри
  них — такие же условия, и без этого проход останавливался на каждом таком
  наборе с причиной «ответа базы нет», хотя мы о нём и не спрашивали.
- **Импорт из каталога** (`features/templates/ImportTemplateDialog.tsx`, доступен всем трём
  редакторам шаблонов) правит ЧЕРНОВИК, а не панель: загруженный текст уходит в `writeDraft` с записью в
  историю (`Ctrl+Z` возвращает как было), и решение сохранять остаётся за пользователем. Ссылка на
  содержимое идёт ровно та, что пришла в индексе, — собранный на клиенте адрес бэкенд отвергает.
- **Проверка ядром Mihomo** (`features/diagnostics/MihomoCheckDialog.tsx`, `POST
  /api/tools/mihomo-test`) проверяет ТЕКСТ черновика, а не модель, и при обоих вердиктах несёт
  оговорку про фиктивные прокси: ядро смотрело документ с подменёнными серверами и вырезанными
  секциями `remnawave`, поэтому может назвать имя или позицию, которых в файле пользователя нет.
- **Ключ локальных хранилищ — `<вид>:<uuid>`**, а не голый uuid: uuid профиля и uuid шаблона
  живут в разных пространствах панели и могут совпасть (по той же причине бэкенд держит бэкапы
  шаблонов в отдельном каталоге). Единственный источник ключа — `shared/lib/docKey.ts`
  (`docStorageKey`), строит его `useConfigDraft` из нового параметра `docKind`
  (`profile`/`template`) и отдаёт наружу как `storageKey`: по нему живут черновик, история
  (`historyStore`) и позиции узлов (проп `docKey` у `TopologyView`). `ConfigDraft.docKey`
  остаётся голым uuid — он уходит в адреса бэкапов. Не путать с пропом `kind` у `Workbench`
  (`profiles`/`templates`): это сегмент пути API. Обе persist-схемы мигрируют старые записи под
  префикс `profile:` (черновики v1 → v2, позиции — новая `version: 1`); битая запись
  пропускается, а не роняет всё хранилище.
- Все записи черновика в обоих редакторах идут через одну функцию `writeDraft(text, {history})`
  (живёт в `useConfigDraft`, зовётся из `Workbench` — из `JsonView` и из восстановления
  версии; страницы её не трогают, они только собирают черновик хуком);
  `historyStore.ts` — стеки `past`/`future` в памяти (без persist: 50 снимков конфига вытеснили бы
  черновики из localStorage). Набор текста в JSON в историю не пишется — это забота CodeMirror,
  вместо этого при уходе с вкладки записывается один снимок «как было до входа». После undo/redo,
  импорта и восстановления бэкапа обязателен `setSelectedNode(null)`.
- `shared/lib/useHotkeys.ts` — хоткеи с guard'ом `isEditableTarget` (проверяет и атрибут
  `contenteditable` по цепочке предков — так покрывается `.cm-content`, а в jsdom свойства
  `isContentEditable` вообще нет); `Escape` не отменяет действие браузера и молчит при открытом
  `<dialog>`. Компонент, потребивший клавишу, обязан гасить всплытие — так `Select` не даёт
  глобальному `Escape` закрыть инспектор вместе со своим списком.
- `DiffView.tsx` — общий `MergeView` для `SaveDialog` и `VersionsDialog` (бывший `BackupsDialog`:
  вкладки «Бэкапы панели» / «Файл», сравнение бэкапа с черновиком в том же диалоге, без вложенного
  `<dialog>`). Разбор и именование файлов — `configFile.ts` (разворачивает `{profile:{config}}`).
- `features/topology` + `features/inspector` — граф и формы редактирования выбранного узла (InboundForm/OutboundForm/StreamForm; генератор ключей Reality дергает `/api/tools`).
- Диагностики несут путь массивом (`ValidationIssue.parts`), а строковый `path` — производный
  (`formatPath`). На `parts` завязаны три резолвера: `features/editor/jsonLocate.ts` (путь →
  диапазон в документе, спуск по дереву CodeMirror — обратная задача к `intellisense/context.ts`),
  `entities/graph/locate.ts` (путь → id узла и счётчики проблем), `entities/graph/search.ts`
  (поиск узлов). Клик по проблеме зависит от вкладки: на топологии ведёт к узлу, в JSON —
  прокручивает к месту; вкладку не переключаем, потому что у `log`/`policy` узла нет.
  Исключение — `ValidationIssue.at`: готовое смещение в тексте у диагностики, которой путь
  назвать НЕЧЕМ. Такова ровно одна — синтаксическая ошибка разбора YAML: «что за ключ» она
  сказать не может (документ на этом месте и не разобрался), а «где» — может, и это
  единственное, что даёт по ней перейти. Заполняет поле `parseMihomo`, читают его текстовая
  вкладка (предпочитает резолверу по пути) и линтер `yamlLocate.ts`. У проверок с путём поля
  нет и быть не должно: второе описание места разошлось бы с первым молча.
- **Синтаксическое дерево берут через `ensureSyntaxTree`, а не `syntaxTree(state)`** — и
  `jsonLocate.ts`, и `intellisense/context.ts`/`hover.ts`. `syntaxTree` отдаёт снимок, снятый при
  создании `LanguageState` (`this.tree = context.tree`), а `ensureSyntaxTree` двигает
  parse-контекст, снимок не обновляя: на большом конфиге начальный тайм-слайс до хвоста не
  доходит, и обе задачи молча работали бы по недоразобранному дереву. Бюджеты разные по
  назначению: у перехода по клику он щедрый, у подсказок — 100 мс, они считаются на каждое
  нажатие клавиши.
- `features/diagnostics` — трассировщик (`TraceBar` в доке + `TracePanel` оверлеем), `GeoDataDialog`
  и `CheckReportDialog` (проверка ядром и Reality-целями). Логика трассировки живёт в
  `entities/xray/trace.ts`, бэкенд отвечает только на вопрос «входит ли домен/IP в geo-категорию».
  Цель трассировки в state `useConfigDraft` без персиста: это инструмент, а не документ; ввод
  проходит через `useDebounced` (600 мс), иначе каждый символ дергал бы бэкенд.
- `entities/xray/recipes` — библиотека рецептов чистыми функциями `plan(config, params) →
  { config, changes, notes }`: вход не мутируется, идемпотентность держится на трёх примитивах
  (`ensureOutbound`/`ensureRule`/`ensureSniffing`) из `apply.ts`. Правила вставляются в начало
  `routing.rules` (в Xray выигрывает первое совпавшее), маршрутные — сразу за ведущей серией
  блокирующих. Реестр в `recipes/index.ts`: `planFor`/`validateFor` разводят рецепты switch'ем по
  `RecipeId`, параметры всех рецептов лежат одной картой `AllParams` — так `RecipesDialog` не
  теряет введённое при переключении списка. UI — `features/recipes` (диалог + формы параметров),
  вход через кнопку «+ Рецепт» в доке топологии, применение идёт через `changeConfig`, то есть
  одним снимком истории. Ключи WARP: ручной ввод либо `POST /api/tools/warp-account`. Диалог
  `RecipesDialog` сам стал обобщённым по модели (`RecipesDialog<TModel>`, `shared/recipes/types.ts`)
  — Xray остался первым его экземпляром с прежним поведением и разметкой (см. рецепты sing-box в
  разделе про шаблоны выше), а `entry.recipe.plan(model, current)` считается, только пока диалог
  открыт: закрытый не растит дерево доступности формами и кнопками рецепта.
- `shared/api` — fetch-клиент; `AuthError` перехватывается в `App.tsx` на уровне QueryCache/MutationCache и редиректит на `/login`.
- `shared/ui` — свой мини-UI-kit (Button, Dialog, Select…), сторонних компонентных библиотек нет.

### Дизайн-система

`shared/ui/tokens.css` — единственный стилевой файл, метафора «патчбей»: ingress индиго
(`--flux`), egress янтарь (`--ember`), правило без своего hue (сталь). Прежние имена
(`--bg`, `--in`, `--out`…) сохранены алиасами. Шрифты: Golos Text + JetBrains Mono.

- **Select — кастомный listbox, не нативный `<select>`.** API: `value` + `options: SelectOption[]`
  + `onChange(value)`. Список рендерится порталом; если триггер внутри модального `<dialog>`,
  порталом служит сам диалог (top layer не пробивается z-index'ом). В тестах вместо
  `userEvent.selectOptions` — `selectOption()`/`optionLabels()`/`selectedValue()` из
  `test/helpers.ts`, в e2e — `pickOption()` из `e2e/helpers.ts`.
- **`Field` с `controlId`** связывает лейбл с контролом через `htmlFor` вместо обёртки. Нужно
  всему, чей текст значения лежит в содержимом (Select): внутри `<label>` он приклеился бы
  к accessible-имени.
- **Раскладка редактора** — `.workbench`: топбар / сцена / статус-бар. Инспектор
  (`.wb-inspector`) выезжает оверлеем поверх канваса, поэтому вьюпорт графа сдвигается ровно
  на его ширину (`inspectorWidth()` в TopologyView ↔ `--inspector-w` в tokens.css) — иначе
  правая колонка узлов уходит под панель и становится некликабельной.
- **Коммутация** описана в `isValidConnection`/`applyConnection` (TopologyView): inbound →
  правило либо outbound; правило — в outbound, балансер либо группу подстановки (`inj:`);
  балансер — в outbound либо группу подстановки. Из группы кабель не выходит: её выходы создаёт
  панель. Гнёзда сквадов закрыты — привязку задаёт панель.

### Особенности домена

- Trojan-inbound'ы не имеют редактора клиентов — панель сама инжектит пользователей в конфиг.
- Для VLESS `flow` задаётся на уровне settings; при смене протокола settings очищаются.
- Squad-узлы графа приходят не из конфига, а из контекста панели (`GraphContext`), и фильтруются по реально существующим тегам inbound'ов черновика.
- У шаблонов подписки нет `createdAt`/`updatedAt` — база черновика и оптимистической блокировки
  это хэш содержимого (`templates/hash.ts`), и считает его только бэкенд; фронтенд просто носит
  строку туда-обратно (`baseVersion`/`expectedHash`), не пересчитывая.
- Панель вставляет инжектируемые группой подстановки outbound'ы **в начало массива** `outbounds` —
  отсюда дефолтный маршрут трассировки в шаблоне (см. `entities/xray/trace.ts`), а не
  `outbounds[0]` документа. При нескольких группах трассировка называет победителем **первую**:
  порядок вставки между группами панель не документирует, это осознанное предположение, а не факт
  из API.
- При `useHostRemarkAsTag`/`useHostTagAsTag` теги инжектируемых outbound'ов знает только панель:
  `predictedTags` возвращает пусто, а проверки «неизвестный outbound-тег» и «у балансера нет
  кандидатов» подавляются по всему документу (`hasPanelNamedTags`) — иначе корректный шаблон дал
  бы ложную тревогу на каждой такой ссылке.
- `expandSelector` не разворачивает префиксы селектора балансера, которые ловят инжектируемые
  теги (иначе развернуть — значит сломать предсказание группы), а при **любой** группе с тегами от
  панели отказывается разворачивать селектор целиком (`expandBlockedByPanelTags`): какие теги
  подставит панель, редактор не знает по определению, поэтому ловить их может любой префикс, и
  замена его точными статическими тегами молча выбросила бы выходы, которых в документе нет.
  `blockingInjectPrefix` (разрыв «балансер → статический выход», пойманный тем же префиксом, что
  и группа) и `blockingGroupPrefix` (разрыв «балансер → группа» префиксом, который заодно ловит
  чужого кандидата) объясняют, когда такой разрыв неразрешим — на них и на
  `expandBlockedByPanelTags` строится диалог подтверждения в `TopologyView`.
- **Шаблоны Mihomo** (`templateType: MIHOMO`, содержимое в `encodedTemplateYaml`) правит писатель
  `applyMihomoOps(md, ops)` (`entities/mihomo/write.ts`) в ДВУХ режимах, выбираемых по документу, а
  не по вызывающему: **сплайс** — правка существующего СОБСТВЕННОГО ключа блочного отображения с
  однострочным скалярным значением (не алиас, не пришедший через `<<:`) — байты вне правки не
  меняются; **модель** — всё остальное (новый ключ, значение-отображение/список, `insert`/`move`/
  удаление элемента списка, flow-коллекция, многострочный скаляр) — правит `Document` библиотеки
  `yaml` (`setIn`/`addIn`/`items.splice`) и печатается `toString({ lineWidth: 0 })` целиком, с
  восстановлением исходного перевода строки (CRLF-файл получает CRLF обратно). Операции
  применяются по одной, документ перечитывается после каждой — пачка в одном вызове безопасна,
  прежний запрет «одна правка за раз» снят. Прежний вывод первой спеки («текст владеет файлом,
  модель обратно не печатается») держался на том, что панель ищет место подстановки по комментарию
  `# LEAVE THIS LINE!`; проверка по исходнику панели (`remnawave/backend`,
  `mihomo.generator.service.ts` — импортирует только `dump()`, строки `LEAVE THIS LINE` в нём нет)
  показала, что панель этот маркер вообще не читает — он подсказка человеку, и только (см. ниже).
  Печатать `Document` целиком во фронтенде вне `entities/mihomo/write.ts` всё равно запрещено —
  второй печатающий путь не заводится; исключение то же, что раньше — `backend/src/mihomo/dummyProxies.ts`,
  результат которого уходит во временный файл для `mihomo -t` и удаляется. `MihomoDoc.json` —
  снимок значений (`toJS`, `{}` у пустого либо битого документа) для мест, которым нужно
  ЗНАЧЕНИЕ, а не узел `yaml`.
- **Отказ вместо порчи.** Операция, чей путь проходит через алиас (`*имя`) или через ключ,
  пришедший слиянием (`<<:`), не применяется и попадает в `refused` с причиной — материализовать
  чужое объявление молча, как это делает панель, писатель не имеет права. `mihomoLockAt(md, path)`
  отвечает замком в двух случаях: `alias` («значение приходит через ссылку на якорь…») и `merged`
  («значение приходит через слияние…») — форма рисует такое поле на чтение и, через `Lock.action`,
  кнопку «Развернуть значение здесь» (`materializeAt(md, path)`: для `merged` кладёт собственную
  пару с копией слитого значения через `toJS`, для `alias` заменяет алиас копией узла-цели через
  `toJS`). Действие явное: материализация меняет документ пользователя и рвёт связь остальных
  потребителей якоря с этим местом, поэтому происходит только по нажатию, а не при первом же
  вводе в поле. Замки `map`, `flow` и `nowhere` первой спеки исчезли: `map` рисует `SchemaForm` по
  схеме, `flow` больше ничего не запирает — пустая последовательность печатается как `[]`, а
  следующая вставка в неё идёт режимом модели и печатается как есть. Операция без эффекта (индекс
  `move` за пределами списка, `remove` по отсутствующему листовому ключу, `insert` по пути с чужим
  НЕ-списком) — тоже `refused` с причиной, а не тихая перепечатка документа без изменения: до этого
  такая операция всё равно доходила до печати, рискуя сдвинуть форматирование без содержательной
  правки, а `refused` оставался пуст. Черновик показывает отказ тем же диалогом, что и отказ
  кабеля (`refusalText`), под нейтральным заголовком «Правка не применена» — заголовок «Так
  соединить нельзя» подошёл бы только кабелю, а отказы теперь приходят и от меню «+ Добавить», и
  от «+ Правило».
- **Маркер `# LEAVE THIS LINE!` декоративен.** Панель ищет место подстановки не по нему, а
  структурно: дописывает сгенерированные серверы В КОНЕЦ корневого `proxies`, их имена — В КОНЕЦ
  `proxy-groups[].proxies` каждой группы без `remnawave.include-proxies: false`, а
  `proxy-providers.<имя>` с `remnawave.include-proxies: true` подменяет `payload` целиком. Ни одна
  проверка, узел графа или отказ маркер больше не читает: `panelInjectsHosts(group)` —
  `remnawave.include-proxies !== false`; `groupTakesHosts(group)` (рисует узел `hosts:<группа>` на
  холсте) — `panelInjectsHosts` либо `include-all`/`include-all-proxies`; `groupGetsHosts(group)`
  (предупреждение «останется пустой») — `groupTakesHosts` либо непустой `use`, либо
  `include-all-providers` (`entities/mihomo/inject.ts`). Узел `hosts:root` рисуется всегда, когда
  документ — отображение. Список `proxies` группы правится (в отличие от sing-box, где панель
  переписывает список целиком): панель дописывает, авторские имена остаются впереди, а форма
  показывает подсказку «панель допишет подставленные хосты в конец» вместо замка.
  `backend/src/mihomo/dummyProxies.ts` дописывает фиктивные имена в каждую группу без
  `include-proxies: false` тем же правилом — маркер там тоже не читается.
- Имена подставленных панелью хостов у Mihomo НЕ предсказуемы вообще (у Xray была схема
  `tagPrefix`): их даёт панель из примечаний хоста. Поэтому ссылка на такое имя (`proxies`/`use`
  группы, `RULE-SET`/`SUB-RULE` и цели в правилах, `rule-set:<имя>` в `nameserver-policy` и
  `fake-ip-filter`, `proxy`/`dialer-proxy`) — предупреждение, а не ошибка; перечень мест ссылки
  один — `referenceSites(md)` (`entities/mihomo/refs.ts`), его же читает и валидация «ссылка в
  пустоту», и переименование. `renameAt(md, kind, from, to)` переименовывает запись и правит все её
  ссылки из того же перечня; при алиасе/слиянии на пути определения ЛИБО на пути любой ссылки —
  отказ `locked`, документ возвращается исходным (та же дисциплина «отказ вместо порчи», что у
  писателя, — частичное переименование через испорченный путь читалось бы как успех).
- **Рецепты Mihomo** (`entities/mihomo/recipes/*`, реестр `MIHOMO_RECIPES` в `recipes/index.ts`) —
  план строит операции писателя и применяет их `applyMihomoOps`; отказ на алиасе становится
  заметкой плана (`applyOrNote` в `recipes/apply.ts` переводит каждый `refused` в `RecipeNote`), а
  не молчанием. Шесть рецептов: разделение по наборам правил, блокировка рекламы, DNS с fake-ip,
  локальный вход, локальные сети напрямую, WARP. Список подсетей у «локальных сетей напрямую» —
  панельный шаблон по умолчанию (`test/fixtures/mihomo/default.yaml`), 18 записей включая четыре
  диапазона IPv6: короче свой список совпал бы с панелью не полностью и мог бы выпустить локальный
  IPv6-адрес наружу. Каталог источников наборов правил (`recipes/catalog.ts`) — статический список
  `.mrs` из `MetaCubeX/meta-rules-dat` (ветка `meta`), те же имена, что у каталога sing-box; бэкенд
  их не скачивает.
